# 表格视图：完成度、四象限与派生状态

截图里那张电子表格要落地，领域里要新增两个由 owner 手动维护的字段（`percent_done`、`quadrant`）、一个不落库的派生量（`status`），并给归档事项在表格里一个受控的落点。这里记的是随之定下的几个决策，以及明确**不**照搬的部分。

派生口径统一写在 `public/tableview.js` 的纯函数里（照 `public/sidebar.js`、`public/calendar.js` 的既有风格，可被 `node:test` 直接 import）：`statusOf` / `estimatedDays` / `actualDoneDate` / `onTimeOf`。服务端不参与推导：不加列、不加端点、不加迁移。

## Considered Options

**完成度**

- **从「进展」推算**：进展是自由文本，要变成 0–100 得先定义一套解析规则，而每个人的措辞都不一样；表格里它是一列要能排序、能筛选的数字，猜出来的数字排不了序。否决。
- **不引入，只靠「进展」表达做到哪了**：少一个字段，但文本既不能排序也不能按区间筛，更回答不了"做完了多少"；两者回答的是不同问题（做到了哪一步 / 做完了多少），谁也不能替代谁。否决。
- **完成度 100 自动归档**：把数字当成动作触发。归档不可逆，一次误填（比如把 90 敲成 100）就是一次撤销不了的操作；反过来，归档也不该被一个手动数字卡住（没填到 100 就归档不了）。两者解耦：完成度只是一条记录，100 不等于归档，归档也不要求 100。否决。
- **0–100 的整数，owner 手动维护**（已选）：与「进展」互不派生，各自留空都合法。

**四象限**

- **一条等级轴（高 / 中 / 低，或 1–5）**：把「紧急 × 重要」两条轴压成一条会丢语义——「紧急但不重要」与「重要不紧急」是相反的两件事，降维后撞在同一档。而截图给的正是两条轴的四个组合。否决。
- **两个独立字段（紧急、重要各存一个）**：能组合出四种取值，但两个字段会允许"只填了一半"的中间态（紧急填了、重要空着），那不是任何一个象限；表格的分组头、筛选器、列也都以单个字段为单位，两列绑不成一组。否决。
- **四象限枚举，可空**（已选）：四个取值加 `null`。「未标注」就是 `null`，不是第五个象限，也不等同于「不重要不紧急」——表格里它单独成一组殿后。

**四象限的展示顺序**

- **教科书的四象限次序**（重要且紧急 → 重要不紧急 → 紧急但不重要 → 不紧急不重要）：那是按「重要」一条轴降序的读法，而这张表是拿来决定"先动哪一件"的。否决。
- **按「要多快处理」排**（已选，用户 2026-10-07 指定）：重要且紧急 → 紧急但不重要 → 重要不紧急 → 不紧急不重要，未标注殿后。它不按任何一条轴，而是按动作的先后——马上做 → 分出去（今天得有人做，但不必是我）→ 排期 → 放着。`QUADRANTS` 里的顺序就是它：分组、筛选下拉、事项对话框的选项都读同一处，改这里等于改全站顺序。
- **颜色按值配，不按次序配**：色号表 `QUADRANT_CLASS` 以象限字面量为键（马上做=红 / 分出去=橙 / 排期=蓝 / 放着=绿 / 未标注=灰），所以调整次序不会串色。这张表确实是前端第二处出现那四个字面量，测试拿 `QUADRANTS` 逐值核一遍——象限改名或增删会红在测试里，而不是在界面上悄悄少一种颜色。

**状态**

- **存成 `items` 的一列**：状态依赖「今天」，存下来的值过一夜就错了。修它要么每天跑一次批量更新（项目里没有定时任务这种东西），要么读的时候再算一遍（那又何必存）。否决。
- **由服务端推导、随响应下发**：等于让每个读接口都多带一列随「今天」漂移的值，还要再定一套服务端日期规则；而这只是呈现口径，判定应当唯一且可被测试直接钉住。否决。
- **前端纯函数现算**（已选）：`statusOf(item, today)` 是派生量的唯一落点。「今天」取 app 状态里的 `today`（来自 bootstrap，跨午夜由日切刷新换掉），不落库、不下发。

**归档行进表格视图**

- **表格视图照旧不含归档行**：那就不可能在表格里核对"这段时间完成了什么"，截图里那一列「任务状态」也就没有「已完成」可言；但「归档从一切工作视图消失」是既有规则，不能顺手推翻。否决。
- **归档行与普通行同置、可点开编辑**：那是把归档事项重新放回工作视图，还等于给「取消完成」开了一个入口（编辑会话里能改字段）。归档不可逆这条规则会被它架空。否决。
- **只在打开「显示已完成」开关时出现，只读，单独成一组**（已选）：归档事项的可见范围沿用「谁能看见这条事项」——**自己参与过的自己看得到，别人的看不到**（2026-10-07 按用户要求从「admin 独占」放宽；数据取 `api.archiveList()`，即 `GET /api/archive`），`admin` 看到的才是全部账号的。开关只是把这一页摆出来：关闭时归档事项依旧从表格里消失，其它工作视图一字未改。

**不照搬的部分**

- **讨论群**：项目里没有评论或群聊领域，也没有账号之间的消息通道——唯一带"通知"语义的东西是「邀请」，而它的语义是"把某人加进 owner 名单"，不是发消息。要照搬就得先建一整套新领域。不做。
- **电子表格皮肤（行高、填色、表格设置、内联编辑）**：这些是呈现偏好，与「以天为最小粒度、归档不可逆」的领域无关。内联编辑尤其不能要：现在只有事项对话框一条编辑路径，校验、乐观锁与字段级错误都落在那里，第二套编辑入口会让它们各自漂移。不做。
- **导出、甘特图、依赖关系**：同为范围之外。导出要先回答"导出谁的可见范围"（可见性判据在服务端 `server/visibility.js`，是全应用唯一一处）；引入依赖关系等于在领域里新增一种「事项之间」的关系（现在只有 owner 名单）。这些要做，各自是一次新决策。不做。

## Consequences

- `CONTEXT.md` 新增「完成度」「紧急重要度」「状态」三个词条；「进展」的 `_Avoid_` 不再把「完成度」「百分比」当作它的别名——那两个词另有归属。
- 状态列是**另一套互斥口径**，与侧栏面板不是同一种切法：四条判据互不重叠，每条事项恰好落在其中一类，且多出侧栏不展示的「已完成」「待开始」。它的「已逾期」与词条**「逾期」同义**（`due_date < 今天`），也就是侧栏「截止提醒」里「已逾期」那一组的判据；侧栏另外单列的「今天截止」在状态列里算**「进行中」**。**别把 README 的「逾期基线」`due_date <= 今天` 当成「逾期」的定义**——那是「截止提醒」两组之和的汇总口径。（截止当天的归属在 2026-10-07 按用户反馈从「已逾期」改成「进行中」，两边由此同源；此前状态列比侧栏的「已逾期」宽一天。）
- 「预计所需天数」`due_date - event_date + 1`（含首尾）、「实际完成日期」取 `archived_at` 的 `yyyy-mm-dd`、「是否按时交付」只在已归档时有值，这三条同样只是派生量，不落库。
- 表格视图的分组、筛选、排序、底部统计（记录数 N）都是纯函数，`node:test` 可直接断言；渲染只做拼装。
- 「归档从一切工作视图消失」与「归档不可逆」两条既有规则未变：归档行的可见性由角色与开关共同决定，且这些行只读。
- 空列表统一显示「没有符合条件的事项。」。
