# 一条事项多个并列的 owner，不引入「协作人」

一条事项可以有一个或多个 owner，彼此**并列、无主次**：名单里没有任何一个人是"主负责人"，权限也不因加入顺序而不同。参与者只有这一种身份，因此不存在「owner + 协作人」那样的两级结构。

## Considered Options

- **一次建多条，各归一人**：选三个账号就建三条独立事项。改动最小，现有模型一个字都不用动，但三个人看到的是三份副本——改标题不同步、日历上出现三条同名条、颜色各不相同。这在协作场景下会被当成 bug 反复报上来，所以否决。
- **owner 唯一 + 协作人（主从两级）**：保留「每条事项只有一个 owner」，另加一个协作人集合。这能保住 CONTEXT.md 原有的约定，也是这类系统的常见做法，但代价是要为第二级参与者另行定义整套权限边界（协作人能否改？能否归档？能否看进展？），而产品上并没有"主"与"次"的实际诉求——派活的人与一起做的人在同一件事上是对等的。否决。
- **一个 owner 名单，成员并列**（已选）：`item_owners` 是一张关联表，成员之间没有顺序语义。可见性、色块标注、"算不算自己的事"三件事都按名单回答。

## Consequences

- CONTEXT.md 里「每条事项有且只有一个 owner」这条约定被推翻，词表已同步改写；「协作人」列入 `_Avoid_`。
- **可见性判据变成"账号是否在名单里"**，SQL 过滤从 `i.owner_id = ?` 改成对名单表的 `EXISTS`。这件事只有一处落点（`server/visibility.js`），所以改动面收敛在一个函数里。
- **删除与归档是并联的**：名单里任何一个人都能归档或物理删除这条事项，且删除对所有人立刻生效。这是并列模型的直接后果，不是遗漏——若将来要区分，那等于把主次重新加回来，应作为一次新的决策而不是打补丁。
- **改名单需要 admin 权限**（`assignsOwner`），多人事项也不会因此变成"人人可改名单"；非管理员增人走「邀请」，需要对方接受。
- 侧栏与日历上不再有单一的 `owner_name`，渲染层要自己从名单里取"第一个 + N"作为文案。
- 邀请是独立状态，不进对方日历；这意味着系统里第一次出现了"与事项相关、但不属于任何事项视图"的东西，需要一个专门入口。
