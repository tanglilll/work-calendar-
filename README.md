# rili（工作日历）— 多人实时日程/任务看板

一个零第三方运行时依赖的多人共享日历看板。每个人记录自己的事项，角色决定可见范围，所有在线客户端通过 SSE 实时看到同一份数据。

技术栈就是 Node 内置模块（`node:http` / `node:sqlite` / `node:crypto`）加浏览器原生 API，没有构建步骤、没有 `npm install`。理由见 [`docs/adr/0001-zero-runtime-dependencies.md`](docs/adr/0001-zero-runtime-dependencies.md)。

## 运行

需要 **Node 24.2+**（用到内置的 `node:sqlite`，以及入口守卫用的 `import.meta.main`——它 Added in v24.2.0）。

```bash
# 首次启动：账号表为空时必须指定初始 admin，否则没人能批准注册申请
RILI_ADMIN_USER=admin RILI_ADMIN_PASSWORD=你的密码 npm start

# 测试（零依赖，用 Node 自带的 node:test）
npm test
```

启动后终端会打印本机与局域网地址，团队其他人直接访问局域网地址即可。

环境变量：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `RILI_ADMIN_USER` | `admin` | 首个 admin 的用户名，仅在账号表为空时使用 |
| `RILI_ADMIN_PASSWORD` | 无 | 首个 admin 的密码，**至少 8 位**；不设则不创建任何账号 |
| `PORT` | `3000` | 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址 |
| `RILI_DB` | `./data/rili.db` | SQLite 文件路径 |

数据库文件落在 `data/`，已被 `.gitignore` 忽略。

## 怎么用

1. **管理员**用环境变量里的账号登录。
2. 别人在登录页点「申请账号」，填**用户名 + 密码 + 备注**。此时不会创建账号。
3. 管理员进「管理 → 待批准申请」点批准，账号**在这一刻才生成**，角色是 `user`。之后可在「管理 → 账号」里改角色。
4. 登录后：日历 42 格，点格子里的小 `+` 或顶栏「新建事项」创建；点色块编辑。`manager`/`admin` 在对话框里可以用复选列表指定多个 owner；普通成员想让别人一起做，勾选后点「发出邀请」，等对方在顶栏「邀请」入口里接受。

## 规则（一句话版）

- **三级角色**，逐级包含：`user` 只及于自己的事项；`manager` 及于全部事项；`admin` 另有账号管理与归档查看。
  - 可见范围贯穿日历和三个侧栏面板，也贯穿 SSE 推送——**服务端过滤，前端不被信任**。
- **事项**：标题非空（≤200 字）；日期为 `yyyy-mm-dd` 真实日期；截止不得早于起始；标签最多一个且必须在白名单 `工作/个人/会议/出差/紧急` 内。
- **颜色**：系统从固定 12 色里自动分配，不可手选。新建时挑当前未被未归档事项占用的颜色；12 色全占用则退到「用得最少」的那一色。归档会释放颜色。
- **owner**：一条事项有**一个或多个** owner，彼此**并列、无主次**；不记录创建者（这是刻意的，见 `CONTEXT.md` 与 `docs/adr/0002`）。`user` 只能给自己建，`manager`/`admin` 可指定任意几个人，也能直接改名单把事项转给别人。名单里任何一个人都能改、能归档、能删除——并列就意味着权限相同。
- **邀请**：非管理员要把别人加进名单，走**邀请**，需要对方接受。待接受期间被邀请人在日历与三个面板里看不到这条事项，只在顶栏的「邀请」入口（带角标）里看到标题、日期与发起人；接受后成为 owner 之一，拒绝即删掉这条邀请、可以再邀。管理员直接改名单不走邀请——那是分派，不是协商。
- **进展**：每条事项有一段自由文本「进展」，任何 owner 都能覆盖式改写，不保留历史（项目以「天」为最小粒度，进展不是流水账）。它与事项同可见范围，在编辑对话框、色块悬停与侧栏里都能看到。
- **归档 = 完成**，且**不可逆**：归档后事项从日历、三个面板、一切工作视图里消失，只有 `admin` 能在「管理 → 归档」里只读查看。前端会二次确认。想让它消失但语义是「这事本就不该存在」，用**删除**（物理移除）。
- **乐观锁**：每条事项带 `version`。你编辑时若别人已改过，保存会返回 `409 VERSION_CONFLICT`，提示「此事项已被他人修改，请刷新后重试」，不会静默覆盖。
- **删账号**：只要求「它是唯一 owner」的未归档事项为零（那些必须先转移）；与别人共享的事项只是把它从名单里摘掉，事项本身留着。曾是它唯一 owner 的已归档事项会随账号一并删除（数量会在提示里告知）。系统始终至少保留一个 `admin`，且不能删除自己。

### 侧栏三个面板的口径

你给的「逾期基线」是 `due_date <= 今天`（截止当天就进提醒），而「截止提醒」又要分「逾期」和「今天截止」两组。落地方式让两者同时成立：

| 面板 | 判据 |
| --- | --- |
| 今日任务 | 覆盖今天（`event_date <= 今天 <= due_date`）且未归档 |
| 截止提醒 · 已逾期 | `due_date < 今天`，红字高亮 |
| 截止提醒 · 今天截止 | `due_date == 今天` |
| 多日任务清单 | `event_date < due_date` 且未归档 |

两组不重叠，其**合计**恰好等于 `due_date <= 今天` 的全部事项——即逾期基线口径下的总数，也正是面板标题上那个汇总计数。

已知重叠：一条「今天做且今天截止」的单日事项会同时出现在**今日任务**和**截止提醒·今天截止**里。这是两个面板各自定义（「今天要做的」vs「今天必须完成」）的必然结果，不是 bug。

### 日历渲染

固定 42 格、周一起始、锚定当前月，左右箭头翻月。上月末与下月初的格子照常渲染事项，所以跨月事项的染色不会断裂。跨多日事项从 `event_date` 到 `due_date` 逐格连续染色；同一格内多条事项纵向均分铺满，最多画 4 个色块，超出则画 3 个加一条「+N 项」。同格内排序为「先起始日期，再标题」，这样同一条跨多日事项在每个格子里的位置一致。色块文案是 `owner: 标题`。

  itemform.js   新建/编辑对话框（呈现与绑定）

## 已知限制

- 纯 HTTP，没有 TLS。设计前提是局域网/单机内网部署；要暴露到公网请自己在前面加反向代理并终止 TLS。
- 密码哈希用同步 `scryptSync`，登录/注册会阻塞事件循环约几十毫秒。内部工具量级下无感，若并发登录变多应改为异步 `scrypt`。
- 前端一次性拉取全部可见未归档事项（不带日期区间）。团队量级（几百到几千条）完全够用；真要长到十万级，`GET /api/items` 已支持 `from` / `to` 参数，改成分页即可。
- **窄屏只保证可点，不保证好用**：宽度不足时顶栏整块折行，不会出现竖排文字或被裁掉的按钮；但日历固定 7 列，越窄每格越小——420px 时每格约 55px，色块文案已经读不出来。**≥700px 是可用宽度**，更窄当作应急查看。
- `node:sqlite` 目前仍是实验性接口，见 ADR-0001 的 Consequences。
