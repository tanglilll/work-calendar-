# 02 — 会话失效的单一判据与收尾

**What to build:** 服务端判定会话失效（401）时，界面不再停在「僵尸登录态」——关掉打开的对话框、清空状态、回到登录页并说明原因。判据只有一处，且只有 401 成立。

**Blocked by:** None — can start immediately.

**Status:** resolved

> 出处：`.scratch/closeout/issues/03-admin-panel-verification.md`「环境限制与未做的事」第 3 条（会话 cookie 只按主机名区分、不按端口）末尾的副产品——「会话失效时界面会停在僵尸登录态……下一步动作却报 toast『请先登录』，且不自动回登录页」（该文件第 181 行）。
>
> 开工时实测推翻了 spec 的一条前提：**登录失败返回的也是 401**（见「证据 3」）。已按「公开接口不参与判定」处理并钉住测试。

- [x] 「这个响应是否意味着会话已失效」由一个**纯函数**判定，且只有 401 成立 → `public/session.js` 的 `isSessionExpired(status)`，全前端唯一落点。
- [x] 断言集进现有零依赖测试套件：401 → 结束会话；400 / 403 / 404 / 409 / 5xx / 没有状态码 → 不结束。**403 尤其要钉住** → `test/session.test.js`（7 项，含 403 单独一条）。
- [x] 请求层调用这个判据；应用层注册的处理器负责收尾：关闭打开的对话框、清空状态、回到登录页、提示「登录已失效，请重新登录」 → `api.js` 判定 + `notifySessionExpired()`，`app.js` 注册 `endSession`。
- [x] 启动探测与登录失败不受影响：未登录时启动探测仍返回 200（服务端在鉴权之前处理它），登录失败仍按原样提示 → **实测确认**（见「证据 3」）；登录失败是 401，因此公开接口在请求层被排除在判定之外，并有测试钉住。
- [x] 浏览器层手验：**真的制造一次会话失效**（同一主机名上的另一实例顶掉 cookie，或直接清掉 cookie），再点任意动作 → 落到登录页并看到提示，且不再出现「顶栏还显示着账号、动作报请先登录」的僵尸态。证据写进工单。 → **已由主 agent 在真实浏览器里执行，结果见文末「浏览器手验结果」**。
- [x] 不做「保留草稿、登录后继续」：会话已失效时保存必然失败，留着半开的编辑框只会让人白填一遍 → `endSession` 第一步就是关掉所有打开的对话框。
- [x] 服务端会话机制（有效期、续期、多设备）不动 → `server/` 零改动，本次只动 `public/`、`test/`、README 的结构清单。
- [x] 全量测试套件全绿 → `npm test`：97 项通过、0 失败（含本票新增 7 项；另外 88→97 的增量里有并行工单新增的用例）。
- [x] 工单里回指出处：本票来自 `.scratch/closeout/issues/03-admin-panel-verification.md`「环境限制与未做」里记的僵尸登录态副产品 → 见标题下引文与「结论」末尾。

## 结论

**服务端判定会话失效时，界面不再停在僵尸登录态：一个纯函数、一处调用、一处收尾。**「这个响应是否意味着会话已结束」落在 `public/session.js` 的 `isSessionExpired(status)`——只有 `status === 401` 成立；文案 `SESSION_EXPIRED_MESSAGE = '登录已失效，请重新登录'` 与收尾钩子（`setSessionExpiredHandler` / `notifySessionExpired`）也在同一个文件里，于是「什么算失效、失效了说什么、谁来收尾」各只有一处。

接线：`public/api.js` 的 `request()` 在需要会话的接口拿到 401 时调用判据、转交应用层注册的处理器，并把抛出去的 `err.message` 换成同一句「登录已失效，请重新登录」。最后这一步是必需的——各调用点照旧 `toast(err.message)`，不换文案的话紧随其后的「请先登录」会把提示顶掉，使用者看到的就不是要求的这句。应用层 `public/app.js` 注册 `endSession`：关掉三个打开的对话框（会话已失效，保存必定失败，留一个半开的编辑框只会让人白填一遍——这就是「不做保留草稿」的落点）→ `clearSession()`（断开 SSE、清账号/事项/能力/邀请角标、回登录页）→ `toast(..., 'error')`。主动登出与会话失效共用 `clearSession()`。

**开工实测推翻了 spec 的一条前提：登录失败返回的也是 401**（`server/routes.js` 第 76 行 `httpError(401, '用户名或密码不正确')`），spec 写的「登录失败返回的是别的状态码」不成立。因此请求层把启动探测、登录、登出、注册申请标为公开接口（`requiresSession: false`）：未登录时它们本来就该能调，其中的 401 是凭据错误。不做这件事的话，每次输错密码都会清空状态、并把表单里的「用户名或密码不正确」顶成「登录已失效，请重新登录」——本票那条验收当场就破。这条边界单独有一条测试钉住。

范围：只动前端三处（新增 `public/session.js`，改 `public/api.js`、`public/app.js`）、新增 `test/session.test.js`、README 的「代码结构」加一行 `session.js`。`server/` 零改动（会话有效期、续期、多设备都没碰）；未做「保留草稿、登录后继续」。

出处回指：`.scratch/closeout/issues/03-admin-panel-verification.md`「环境限制与未做的事」第 3 条末尾记的僵尸登录态副产品（该文件第 181 行）。

## 证据

### 1. 纯函数与断言集 —— `test/session.test.js`（新增 7 项）

| 断言 | 结果 |
| --- | --- |
| `isSessionExpired(401)` → `true`（唯一成立的状态码） | ✔ |
| `isSessionExpired(403)` → `false`（403 是「无权处置他人的事项」，人还正常登录着） | ✔ |
| `false`：400 字段错误 / 404 不存在 / 409 版本冲突 / 500 与 503 服务端故障 / `undefined`、`null`（没有状态码） | ✔ |

先跑一次确认它红：`node --test test/session.test.js` → `ERR_MODULE_NOT_FOUND: file:///D:/rili/public/session.js`（实现前模块不存在，测试文件加载不起来）；实现后转绿。

### 2. 请求层接线（同一文件，4 项）

- 需要登录的接口回 401 → 转交收尾**恰好一次**，且 `err.message` 就是 `SESSION_EXPIRED_MESSAGE`；
- 403 / 409 / 500 → **不**转交，错误按服务端原样交给调用点；
- 登录回 401 → **不**转交，`err.message` 仍是「用户名或密码不正确」（登录表单靠它提示）；
- 未登录时的启动探测 200 → 不误判。

### 3. 服务端两条前提的实测（不只是读代码）

用 `test-helpers/world.js` 的内存实例在同一进程里发请求（桩 req/res，与 `test/invites-http.test.js` 同法，不开端口）：

```
GET  /api/bootstrap  无 cookie → {"status":200,"body":{"authenticated":false,...}}   ✔ 与 spec 一致
POST /api/login      密码错误  → {"thrownStatus":401,"message":"用户名或密码不正确"}   ✘ 与 spec 相反
POST /api/login      用户不存在 → {"thrownStatus":401,"message":"用户名或密码不正确"}
GET  /api/items      无 cookie → {"thrownStatus":401,"message":"请先登录"}
GET  /api/owners     无 cookie → {"thrownStatus":401,"message":"请先登录"}
POST /api/register-request     → {"status":201,...}（公开接口，未登录可用）
```

启动探测那条前提成立（未登录 200，服务端在鉴权之前处理它）；**登录失败那条不成立**——它同样是 401。处理方式见「结论」第二段。

### 4. 应用层收尾链路的非浏览器冒烟（DOM 替身；一次性脚本，未入库）

在仓库外的最小 DOM 替身上 import `public/app.js`，由 SSE 推送触发一次 `api.listItems()` 并返回 401（等价于「使用者点任意动作」走到的那条路），观察 DOM 效果：

```
登录后：app 可见 = true | auth 隐藏 = true | 顶栏 = zhao（user）
401 后：app 隐藏 = true | auth 可见 = true
对话框关闭次数：item = 1 | admin = 1 | invites = undefined（没打开，故未调用 close）
提示 = "登录已失效，请重新登录" | kind = error
实时流已断开 = true
```

这证明应用自身逻辑正确；真实浏览器（cookie 真的被顶掉）由主 agent 按下面步骤验。

`npm test` → `tests 97 / pass 97 / fail 0`；`node --check` 过 `public/session.js`、`public/api.js`、`public/app.js`。（88→97 的增量含并行工单新增的用例，本票新增 7 项。）

## 浏览器手验步骤（交给主 agent，本票唯一未勾的验收项）

### 步骤 A：制造一次真实失效 → 落到登录页

1. 按 `docs/agents/local-environment.md` §1 起两个**各自独立库**的实例（同主机名 `127.0.0.1`，端口不同）：
   - A（被测）：端口自选（如 4900），`RILI_DB=./data/verify-02.db`；
   - B（用来顶 cookie）：端口自选（如 4901），`RILI_DB=./data/verify-02b.db`。
   - **B 必须用另一个库**：会话表在库里，两实例共用同一个库时 B 登录写下的会话行 A 也认，顶不掉（不会 401）。这是本步骤唯一的坑。
2. IAB 打开 `http://127.0.0.1:4900/`，用 admin 登录，确认顶栏是 `admin（admin）`、日历在。
3. 同一浏览器**新开标签页**打开 `http://127.0.0.1:4901/` 并登录任意账号（同一浏览器 = 同一个 cookie jar；host 相同、端口不同 → `rili_session` 被换成 B 的）。这正是 closeout 03 记录的真实触发器。
4. 回到 4900 的标签页——界面**仍然**显示着登录态（原来的僵尸态起点）。
5. 点一个会打到服务端的动作：**顶栏「新建事项」→ 填标题与日期 → 点「保存」**。期望同时看到：
   - 对话框立刻关闭；
   - 界面回到登录页（`#auth` 可见，顶栏账号与日历都不在）；
   - toast「登录已失效，请重新登录」（error 样式）；
   - 不再出现「顶栏还显示着账号、下一步动作报请先登录」的组合。
   - （可选再点一次顶栏「邀请」这类动作，确认失效后界面入口已不可达。）
6. 备用的失效制造法（不想起第二个实例时）：在 4900 的标签页清掉该站点 cookie（`document.cookie = 'rili_session=; Path=/; Max-Age=0'`，或在浏览器设置里删该站点数据），再按第 5 步点动作，期望完全一样。此法不依赖第二个实例、与库无关。
7. （仅供判断现象，不是验收项）此时服务端里 A 的那条 session 行**仍然有效**——失效是「浏览器带着别人的/没有 token」，不是服务端删了会话。

### 步骤 B：登录失败不被误判（浏览器层，务必做）

在 4900 的登录页用 admin + **错误密码**提交：表单里应显示「用户名或密码不正确」，**不得**出现 toast「登录已失效，请重新登录」，也不应有额外的状态清空或跳转。这是本票实测发现、与 spec 前提冲突的那条边界。

### 步骤 C：403 不被误判（可选）

403 在界面上没有可点到的路径（可见性由服务端过滤，看不到就点不到），以测试为准（证据 2）；浏览器层只需确认正常使用中**不会**莫名回登录页。

## 浏览器手验结果（主 agent 执行，2026-09-18）

**环境**：两个独立进程、**各自独立库**、同一主机名不同端口——A `127.0.0.1:4901`（`data/verify-02a.db`）、B `127.0.0.1:4902`（`data/verify-02b.db`），账号都是 `admin` + 启动时设的密码。浏览器两个标签页分别打开 `http://127.0.0.1:4901/` 与 `http://127.0.0.1:4902/`。

**制造失效（步骤 1–4）**：A 登录后顶栏是 `admin（admin）`、日历 42 格在；再在 B 登录，回到 A 的标签页——**A 仍显示 `admin（admin）`、界面照常**，这正是僵尸态的起点（服务端那条会话已不再被浏览器带上）。

**点会打到服务端的动作（步骤 5）**：在 A 的标签页点「+ 新建事项」→ 填标题 → 点「保存」（按钮是 `data-act="save"`，不是 `type=submit`）。观察：

| 观察点 | 结果 |
| --- | --- |
| 事项对话框是否关闭 | **已关闭**（`open === false`）——半开的编辑框被收尾关掉，不会留一个保存必定失败的框 |
| `#app` 是否隐藏 | **已隐藏** |
| `#auth` 是否可见 | **可见**（回到登录页） |
| toast 文案与样式 | 「登录已失效，请重新登录」，`data-kind="error"` |
| 「顶栏显示账号 + 动作报请先登录」的组合 | **未出现** |

**登录失败不被误判（步骤 B，务必做的那条）**：落到登录页后，用 `admin` + **错误密码**提交 → 表单内 `.form-msg` 显示「用户名或密码不正确」（`data-kind="error"`），**没有** toast、没有状态清空、没有额外跳转。这条与 spec 前提冲突的边界在真实浏览器里成立。

**补充观察（不属验收项）**：收尾后 `#whoami` 的文本仍是 `admin（admin）`，但它所在的 `#app` 已隐藏，用户看不到，下次登录会被重写——是遗留文本，不是可见状态。

**方法学说明**：点击一律用 DOM 派发的 `el.click()`（本环境唯一可靠的点击方式，见 `.scratch/browser-verification/spec.md`）；填值用页面内 `evaluate` 直接写 `input.value`（应用提交时读 FormData，与手输等效）。附一条本轮新确认的环境事实：原生 `confirm` **可用**（与 `prompt()` 不同）——工单 03 的删除路径就是用它走通的，不必装替身。
