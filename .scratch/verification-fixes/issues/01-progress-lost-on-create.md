# 01 — 修掉新建事项时「进展」被丢弃

**What to build:** 在新建对话框里填的进展，保存后真的落库——与编辑路径行为一致。现在这条路径上值被静默丢掉：界面把它发了出去（新建对话框总是提交进展字段），校验层也把它备好了，只有写入层没有把它写进库，于是用户必须再进一次编辑框补写。这是本轮唯一的静默数据丢失。

**Blocked by:** None — can start immediately.

**Status:** resolved

- [x] 新建时带进展 → 该事项的进展就是填的内容，且它的更新时间是一个有效时间戳（不是空）。
- [x] 新建时不填、或只填空格 → 进展与它的更新时间都是空（不是空字符串）。
- [x] 两条新断言**先跑红**，且红的原因必须是「进展是空」；改完写入语句后才转绿。把这段红→绿写进工单记录。
- [x] 不改表结构、不做迁移、不回填历史数据——这两列早已在表上，缺的只是新建路径的写入。
- [x] 全量测试套件（现 88 项 + 新增）全绿。
- [x] 工单里回指出处：本票来自 `.scratch/closeout/issues/04-version-conflict-ui.md` 附带发现的第 1 条；那票写明「若维护者认可应另开工单，不要让它随本票被当作已收尾」。

## 结论

- 改动两个文件，均在授权范围内：
  - `server/items.js`：`createItem` 的 `INSERT INTO items` 补上 `progress` 与
    `progress_updated_at` 两列。语义与更新路径（`updateItem`）一致——有进展才把
    更新时间记成同一次的 `now`，没进展两列都写 `null`。校验/归一化层（99–111 行）
    与前端（`public/itemform.js` 总是提交进展字段）都没动，因为它们本来就对。
  - `test/items.test.js`：在既有的「进展」describe 里加两条断言，直接断言
    `createItem` **返回的落库字段**（不是插入语句本身）。
- 未改表结构、未做迁移、未回填历史数据。`server/routes.js:108` 把请求体原样交给
  `createItem`，链路上没有第二处丢进展的地方。
- 一处如实说明：两条新断言里，只有「带进展」那条在修前是红的；「只填空白」那条在
  坏代码上本来就是绿的——写入层整列不写时，空进展的两列恰好人也是空，这与期望值
  重合。它作为护栏继续留着，但红→绿的证据由前一条提供。
