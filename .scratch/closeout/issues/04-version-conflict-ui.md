# 04 — 409 冲突的界面表现

**What to build:** 两个窗口编辑同一条事项、先后保存，确认后保存的一方看到冲突提示、且先保存者的改动没有被静默覆盖。乐观锁是「不静默覆盖他人改动」这项承诺的全部实现，它的界面表现从未被观察过。

**Blocked by:** None — can start immediately.（建议与 02、03、05 共用一个浏览器会话与一个实例）

**Status:** resolved

## 结论

**通过。** 保存与归档两条路径上的冲突都在真实浏览器里出现了预期表现：后保存的一方拿到 409、看到明确错误提示、对话框关闭、先保存方的改动原样还在；没有静默成功、没有无声失败、也没有「看起来保存成功其实没保存」的中间态。

## 验收标准逐条

- [x] 后保存的一方看到明确提示（大意「此事项已被他人修改，请刷新后重试」），而不是静默成功、也不是无声失败。
  —— 两次冲突都出现 toast，`kind=error`、文案精确为 `此事项已被他人修改，请刷新后重试`；经页面内 `#toast` 的 MutationObserver 记录（不是事后目测）。
- [x] 先保存的一方的改动**仍然在**：冲突没有把对方的改动覆盖掉。
  —— 保存路径那次：服务端 `version=2`、`title=验证事项04-A改`；归档路径那次：`version=3`、`title=验证事项04-A改2`。后保存方的两次写入都一个字没进去。
- [x] 冲突之后对话框的行为是明确的——关闭、或保持可编辑但提示清楚——不存在「看起来保存成功、实际没保存」的中间态。
  —— 两次都是对话框 `open=false`，同时只有那一条 error toast、没有成功提示，列表随即按服务端状态刷新。
- [x] 归档路径上的冲突同样被观察到（它与保存共用同一份版本校验）。
  —— `POST /api/items/1/archive` 带 `{"version":2}` → 409，事项未被归档（`GET /api/admin/archive` 0 条）。
- [x] 证据写进本工单，并注明两个窗口用的是同一账号还是不同账号——两种情形下「谁看得见什么」的推理不同。
  —— **同一账号**（`admin`），见下节与「跨账号时这条结论怎么走」。

## 环境与两个窗口

- **实例**：一次性隔离实例，独立进程（`Start-Process`，不用会话后台任务）、空库、`HOST=127.0.0.2`、`PORT=4600`、`RILI_DB=./data/verify-04.db`；验完停进程、删库与日志。启动命令见 `docs/agents/local-environment.md` §1，本次填的就是上面这几个值。
- **隔离的边界**：**进程与数据库层面**未触碰任何在用实例（全程只读写 `verify-04.db`）。但登录动作本身会影响别人——`rili_session` 这个 cookie 只按主机名区分、不按端口，我最初在 `127.0.0.1:4600` 登录就把该主机上的这个 cookie 换成了我这边的（见「附带发现 2」，那里同时记了这件事如何反噬我自己）。
- **浏览器**：ZCode 内置浏览器（IAB），两个标签页 A / B 指向同一实例。
- **两个窗口是同一账号**：`admin`，两标签页顶栏 `whoami` 都是 `admin（admin）`（IAB 各标签页共享 cookie，第二个窗口打开即处于登录态）。所以本次验的是「同一账号的两个窗口」，比对的是同一账号手上的两份副本。
- **跨账号时这条结论怎么走**：能进到版本校验这一步的账号（事项名单里的人，或 `manager`/`admin`），走的是同一段 `UPDATE ... WHERE id = ? AND version = ?`，`changes === 0` 即 409——判据只看事项的 `version`，不看请求来自谁，所以跨账号的结论与本次相同。但要留意上游那道门不同：非名单成员的 `user` 在 `requireItemAccess` 就被 403 挡住（`server/items.js`），根本走不到 409。也就是说，本次验证覆盖的是「有权限改这条事项的人拿了旧副本」这一种情形，没有覆盖「无权者会撞见什么」——那不是本工单的验收范围。

## 证据

### 保存路径

基线：事项 `#1`，`title=验证事项04`，`version=1`。窗口 A 与 B 各自打开这条事项的编辑对话框，**双方手上的副本都是 `version=1`**。

1. **窗口 A 先保存**：标题改为 `验证事项04-A改`。请求 `PATCH /api/items/1`，体为
   `{"title":"验证事项04-A改","event_date":"2026-09-18","due_date":"2026-09-18","tag":null,"progress":"","version":1}` → 响应 `200`。之后：
   - 服务端读出 `version=2`、`title=验证事项04-A改`；
   - 对话框关闭；**没有任何 toast**（成功是静默的，符合设计——提示只留给失败）；
   - `performance.timeOrigin` 仍是 `1789695932106`（该值即页面创建时刻的 epoch 毫秒），说明窗口 A 全程没有重载。
2. **窗口 B 此刻的状态**（关键）：对话框仍开着、标题框里还是 `验证事项04`（旧副本），而它**背后的日历已经是 `admin: 验证事项04-A改`**。也就是说，B 的界面是「冻结的旧副本叠在最新状态之上」——静默覆盖只会在这里发生。
   （这一步观察到的只是「日历变了」；B 没有重载、也没有人动过它，最合理的解释是 SSE 推送触发的刷新，但本次没有单独记录 `items` 事件，故按现象记录。下面的判定不依赖这个解释——第 4 步是直接读服务端。）
3. **窗口 B 后保存**：标题改为 `验证事项04-B改`，请求体带 `"version":1` → 响应 **409**：
   ```
   {"error":{"message":"此事项已被他人修改，请刷新后重试","code":"VERSION_CONFLICT"}}
   ```
   界面表现（同一批读数，未分期读取）：
   - toast：`hidden=false`、`kind=error`、文案 `此事项已被他人修改，请刷新后重试`；MutationObserver 记到的出现时刻 `t=25157`（相对该页面 `timeOrigin=1789695938578.3` 的毫秒数，观察器在页面加载后立即安装、页面全程未重载）；
   - 对话框 `open=false`——不留在半开状态，也不处在「可继续编辑但不知道自己没保存」的位置；
   - 日历 `admin: 验证事项04-A改`，侧栏 `今日任务 1 / 截止提醒 1 / 多日任务清单 0`；
   - 除那条 error toast 外没有任何成功提示。
4. **服务端复核**：`GET /api/items` 返回 `version=2`、`title=验证事项04-A改`——**窗口 B 那次编辑一个字都没写进去**。

### 归档路径（与保存共用同一份版本校验）

1. 两个窗口重新打开编辑框，这次双方副本都是 `version=2`（两个对话框里都能看到 `标记完成` 按钮）。
2. 窗口 A 把标题改成 `验证事项04-A改2` 并保存：`PATCH` 带 `"version":2` → `200`，服务端 `version=3`。
3. 窗口 B（手上仍是 `version=2`）点「标记完成」：
   - 确认框文案 `确认把「验证事项04-A改」标记为完成？\n\n完成后该事项会从日历和所有面板消失，且无法撤销。`（注意标题是 B 手上的旧标题，不是 A 刚改的新标题）；
   - 确认后请求 `POST /api/items/1/archive`，体 `{"version":2}` → **409**，响应体是同一个 `VERSION_CONFLICT` 文案。
4. 界面表现（归档路径自己的读数）：toast `hidden=false`、`kind=error`、同一条文案，MutationObserver 记录到 `t=39807`；对话框 `open=false`。
5. **事项没有被归档**：日历里还在（`admin: 验证事项04-A改2`），`GET /api/items` 仍是 `version=3, title=验证事项04-A改2`，`GET /api/admin/archive` 返回 **0 条**。

## 方法学说明

- 点击一律用 `locator.evaluate(el => el.click())`（DOM 派发），原因与上一轮相同（见 `.scratch/browser-verification/spec.md` 的对照表）。**它证明的是应用自身的交互逻辑正确，不能证明「该按钮在真实鼠标下可点」**。
- 两个标签页由本次验证新建、验完 `close()`，没有碰用户正在看的页面。页面内装了三样观测器：`#toast` 的 MutationObserver（记录文案与出现时刻）、`window.fetch` 包装（记录 `/api/items` 的请求体与 ≥400 的响应体）——这两样只读、不改行为；以及 `window.confirm` spy（记录文案并返回 `true`），**它确实改变了行为**：替用户点了确认。装它的理由与代价都写在这里——归档要先越过二次确认才可能走到 409，不越过就验不到；代价是「原生确认框的视觉呈现」本次同样未被观测（与 c4 同口径）。
- 断言全部读 DOM 与接口返回值，不依赖截图；上述每个数字都可按「复现」一节重跑。

## 附带发现（不在本工单范围，同一会话里撞见）

### 1. 新建事项时填的「进展」被服务端丢掉

新建对话框里「进展」是可填的。实测：在新建框里把进展填成 `创建时写的进展`（保存前读文本域的值确认就是它），保存请求体里也确实带着 `"progress":"创建时写的进展"`，响应 `201`——但服务端返回的这条事项 `progress` 是 `null`。

对照组：同一条事项改用编辑框补写进展，`PATCH` 后 `progress` 正常落库。所以问题只在新建路径。成因在 `server/items.js` 的 `createItem`：它的 `INSERT INTO items (title, event_date, due_date, tag, color, created_at, updated_at)` 里没有 `progress` 列，尽管上面 `normalizeItemInput(..., { requireAll: true })` 已经把 `values.progress` 备好了。测试照不到它——`test/items.test.js` 里与 `progress` 有关的断言只有「不动它时是 `null`」和「更新能落库」两种，没有一条断言「新建时就带进展」。

本工单只做验证、不动产品代码，处置留给维护者。**注意：这条发现目前只存在于本工单里，tracker 中没有对应的工单文件**——若维护者认可，应另开工单而不是让它随本工单一起被当作「已收尾」。

### 2. 同宿主不同端口的实例共用 cookie

最初在 `127.0.0.1:4600` 起实例，登录后用着用着 `/api/items` 开始返回 `401 {"error":{"message":"请先登录"}}`，而页面自己仍显示 `admin（admin）`（前端状态是登录时的，不会自己变）。直接读该实例的库：`sessions` 表里只有我登录时写的那一条（`created_at 2026-09-18T01:43:34Z`、`expires_at` 在下个月）——说明浏览器这次带上来的 token 不是我这条。

同一时刻本机还有另外三个实例监听在 `127.0.0.1`（`netstat -ano` 查 LISTENING 得到 4410 / 4700 / 4800，都不是我的进程；`data/` 下同时出现 `verify-03.db`、`verify-05.db`、`verify-06.db`）。cookie **只按主机名区分、不按端口**，所以任何一个在浏览器里登录过 `127.0.0.1` 的实例，都会把 `rili_session` 换成它那边的 token，我这边随即变成未登录。反过来同样成立：我自己那一次登录也抢了别人在这个主机上的 cookie——这正是上面「隔离的边界」里那句话的来历。

改绑 `127.0.0.2`（另一个 loopback 地址，cookie 主机不同）之后，整个验证过程未再复现。本次没做对照实验（要复现就得让两个会话互踢），故按「机制解释 + 规避方式」记录。是否并进 `docs/agents/local-environment.md` 由维护者定——那是环境事实的唯一出处。

## 复现

1. 起实例（独立进程，别用会话后台任务；完整命令模板与要点见 `docs/agents/local-environment.md` §1）：
   ```
   HOST=127.0.0.2 PORT=4600 RILI_DB=./data/verify-04.db \
   RILI_ADMIN_USER=admin RILI_ADMIN_PASSWORD=<至少 8 位> node server/index.js
   ```
   用 `127.0.0.2` 而不是 `127.0.0.1`——理由见「附带发现 2」。
2. 两个标签页打开 `http://127.0.0.2:4600/`（同一账号，共享 cookie 即登录态）。
3. 两标签页各点日历色块打开**同一条**事项的编辑框 → A 改标题保存 → B 改标题保存：B 收到 409 toast、对话框关闭、日历仍是 A 的标题。
4. A 再保存一次把版本推进 → B 点「标记完成」并确认：同一条 409，且事项仍然在、没有被归档。
5. 收尾：按 `local-environment.md` §1 的「怎么确认它真的停了」停进程并复查 node 进程，再删掉 `data/verify-04.db*` 与两份日志。
