# 05 — SSE 可见性与邀请

**What to build:** 用第二个账号在另一个标签页观察三件事：`user` 角色收不到他人事项的事件；被邀请人待接受期间看不到该事项；接受邀请后**不刷新**即出现。第三条顺带验证一条从未在界面上出现过的领域规则——「邀请不是参与者状态」。

**Blocked by:** None — can start immediately.（建议与 02、03、04 共用一个浏览器会话与一个实例；本票需要一个 `user` 角色账号，走真实的申请→批准路径造出来）

**Status:** resolved

- [x] 他人新建或修改事项时，`user` 账号的窗口里**不出现**该事项——日历与三个侧栏面板都没有它（这是本轮最要紧的一条：可见性由服务端过滤，前端不被信任）。
- [x] 被邀请人**待接受期间**：日历与三个面板里都看不到该事项，只在顶栏「邀请」入口（带角标）里看到它的标题、日期与发起人。
- [x] 接受邀请后，该事项出现在被邀请人的窗口里，**无需手动刷新**；同时它成为 owner 之一。
- [x] 拒绝邀请后该事项不出现，且发起人可以再次邀请同一个人。
- [x] 证据写进本工单，并注明该账号的角色确实是 `user`——不要用被提权过的演示账号，「提权过的账号收不到/收得到什么」与普通成员不同，会得出错误结论。

## 结论

**通过。** 四个观察点全部成立，其中两条是**可证伪**验过的，不是「没看见就当没有」：

- 被邀请人窗口上装了一个 SSE 观察钩子，记录该页面**全部**连接收到的 `hello` / `items` / `admin` / `self` 事件。他人新建两条、修改一条期间，钩子**零新增**。
- 同一条连接另做了两组**阳性对照**，所以「没有事件」既不是钩子失灵、也不是「服务端谁也不推」：（a）自己建事项 → 当场收到 `items{created}`；（b）**另一个账号**（admin）建并修改一条该账号可见的事项 → 当场收到 `items{created}` / `items{updated}`，窗口自己重画（见 2.1）。后者才是这条否定断言的关键对照——只有它能排除「服务端只回推给操作者」这种替代解释。
- 同一个 `GET /api/items`：admin 视角 3 条，被邀请人视角 1 条——过滤发生在服务端，不是前端拿到数据后不画。
- 接受邀请后事项**不用手动刷新**就进了日历与面板：页面里的观察日志从**登录那一刻连续累积**到接受之后（整页刷新会把它清零），而事项确实出现了。

过程中撞到三件不属本票的事，其中两件与并行会话的既有记录吻合（见「中途撞到」一节）：登录后 `inviteCount` / `capabilities` 停在登录前的值（= 工单 02 顺带发现，同一根因），同宿主不同端口的实例共用 cookie（= 工单 04 的附带发现 2，本次撞到的是它的反向），中文经命令行传参被改坏（新，环境细节）。

## 环境与身份

| 项 | 值 |
| --- | --- |
| 实例 | 独立进程（非宿主后台任务），`HOST=127.0.0.1 PORT=4700 RILI_DB=./data/verify-05.db`，空库 → 按环境变量创建初始 `admin` |
| 账号 | `admin`(id=1，来自环境变量) / `u05-invitee`(id=2，走**申请 → 批准**造出) / `u05-inviter`(id=3，同上)；2.1 的第二个实例另有 `u05-peer`(id=2) |
| 角色 | `u05-invitee` 与 `u05-inviter` 在「管理 → 账号」里都是 `user`（见 1），bootstrap 下发的能力集三项全 `false` |
| 浏览器 | IAB 单标签页，`http://localhost:4700/`；同一时刻只登录一个身份 |
| 行为发起方 | 需要「他人」时用 `curl` 带各自的 cookie jar 打 `http://127.0.0.1:4700/`（admin 一条、inviter 一条） |
| 界面 / curl 的分工 | **走界面**：注册申请 ×2、admin 批准 ×2 与角色核对、被邀请人建自己的事项、接受邀请、拒绝邀请、发起人用编辑对话框发出邀请（第 5 条）、全部登录切换、2.1 那组第三方对照。**走 curl**：admin 那两条「他人事项」的新建与修改（第 2 条）、inviter 建待接受事项并发起邀请（第 3 条）、2.1 里 admin 侧的新建与修改 |
| 构建 | 主证据（§1–§5，09:47–09:50）跑在 09:46 前的构建上；2.1 与 09:51 之后的复验跑在当前工作区的构建上（两者相差 `public/app.js` 里一处 `onLogin` 改动，不涉及本票验的任何路径：SSE 过滤、邀请接口、日历与面板渲染）。**混用是局限，记在这里** |

**为什么行为发起方走 curl 而不是第二个浏览器窗口。** IAB 各标签页共享 cookie，而 cookie **只按主机名区分、不按端口**；同机的并行会话正在别的端口上跑同一产品的实例，`rili_session` 会被它们互相覆盖（本次实测：登录 `200` 之后紧接着 `401`，而库里那条 session 明明还在）。所以浏览器侧只保留**被观察的那个身份**，并换用 `localhost` 这个与 `127.0.0.1` 不同的主机名把身份圈出来；「他人」的动作从 curl 发起。这不削弱本票的结论——被验的对象是**被邀请人窗口的呈现与推送过滤**，而 curl 走的是与界面完全相同的 REST 端点（`POST /api/items`、`PATCH /api/items/:id`、`POST /api/items/:id/invites`）。

## 方法学说明

- **点击**一律 `locator.evaluate(el => el.click())`（DOM 派发），与上一轮、与工单 04 同口径：证明应用自身交互逻辑正确，**不能证明「该按钮在真实鼠标下可点」**。另外它**绕过 `<dialog>` 的模态拦截**——本次实测能在管理面板的模态框打开时点到顶栏的「登出」，那是真实鼠标做不到的状态。
- **表单填值**用直接赋值（`input.value = …`）后由界面自己提交。原因：本环境 `locator.fill()` 报 `Browser Use encountered an error interacting with this webpage's clipboard: Active element is no longer the expected input target`。应用在提交时用 `FormData(form)` 读值、不经响应式绑定，所以赋值等价于键入——但这条同样是绕开输入管线的操作，按约定标注。
- **SSE 观察钩子**：在登录前包装 `window.EventSource`，对 `hello` / `items` / `admin` / `self` 四类事件记账（时刻、载荷、当时的 `whoami`）。**它只覆盖安装之后建立的连接**——被邀请人的连接是安装之后建的，所以覆盖完整。
- 断言全部读 DOM 与接口返回值，不依赖截图；下列每个数字都可按「复现」一节重跑。
- 正文时间统一写**本机时间（UTC+8）**；库里 `created_at` 是 UTC，本工单引用时已换算。

## 验收标准逐条

### 1. 账号确实是 `user`（不是被提权过的演示账号）

「管理 → 账号」表格三行（09:46 批准完两个申请之后）：

```
admin        admin  自己   未归档 0 / 归档 0
u05-invitee  user          未归档 0 / 归档 0
u05-inviter  user          未归档 0 / 归档 0
```

被邀请人登录后 `GET /api/bootstrap` 下发的能力集：`{"seesAllItems":false,"assignsOwner":false,"managesAccounts":false}`，顶栏没有「管理」入口；新建事项对话框里没有 owner 多选（只有「（保存后确定）」）。

### 2. 他人新建/修改事项 → `user` 窗口零事件、零显示

基准（09:47:16，被邀请人自己经界面建了 1 条事项）：日历 1 个色块 `u05-invitee: 05-被邀请人自己的事项`（9/18 格），面板 `今日任务1 / 截止提醒1 / 多日任务清单0`，钩子账上 3 条（连接、`hello`、`items{ownerId:2,kind:"created",itemId:1}`）。

接着 admin（curl）做了三件事，**全部只属于 admin**：

| 时刻 | 动作 | 事项 | 若可见会落在哪些视图 |
| --- | --- | --- | --- |
| 09:48:07 | 新建 | `05-他人的单日事项` 2026-09-18 → 2026-09-18（标签 会议） | 日历 9/18 格、今日任务、截止提醒·今天截止 |
| 09:48:08 | 新建 | `05-他人的跨日事项` 2026-09-16 → 2026-09-17 | 日历两格、截止提醒·已逾期、多日任务清单 |
| 09:48:16 | 修改 | 上一条改标题并补进展，`version` 1 → 2 | 同上（同一条事项重画） |

被邀请人窗口在同一时段的观察值：

| 观测点 | 值 |
| --- | --- |
| 钩子账上最后一条 | `09:47:16.653 items{ownerId:2,kind:"created",itemId:1}`——**他人动作之后没有任何新条目** |
| 日历色块 | 仍只有那 1 个：`u05-invitee: 05-被邀请人自己的事项` |
| 面板 | `今日任务1 / 截止提醒1 / 多日任务清单0`，与基准逐字相同 |
| `GET /api/items`（被邀请人） | `["1:05-被邀请人自己的事项"]` |
| `GET /api/items`（admin，同一端点） | 3 条：1、3、4 |

**为什么这条可证伪**：同一条 SSE 连接在 09:47:16 刚记下过「自己的事项 → 收到 `items` 事件」，说明连接活着、钩子在记；另一侧同一端点返回 3 条。所以「窗口里什么都没有」是被**服务端过滤掉了推送与读取**，而不是前端拿到数据后不画——若服务端漏推，钩子账上会留下痕迹。

**事项 id 跳号（复算提示）**：本票正文里的事项 id 是 `1、3、4、5、6、7`，没有 2。原因是 09:47:40 第一次用 `curl -d '…中文…'` 建事项时命令行把 UTF-8 改坏了（见「中途撞到 3」），那条乱码事项当场被 `DELETE /api/items/2` 删掉；`items.id` 是 `AUTOINCREMENT`、号段不重用，于是留下这个空号。按下面「复现」重跑时 id 会从 1 连续排，**id 本身不是判据**，判据是每条标题/日期/归属。

### 2.1 对照：同一个窗口，动作换成「与我有关」的就会自己更新

上面那条否定断言要成立，必须排除一个替代解释：**服务端根本不给任何人推事项事件**（那样「user 啥也没收到」就不能说明过滤生效）。为此在**第二个一次性实例**（同样 4700 端口、空库 `data/verify-05.db`、同样只绑 `127.0.0.1`）上补做了一组第三方对照：

| 步骤 | 谁做的 | 窗口侧观察值 |
| --- | --- | --- |
| 造账号 `u05-peer`（申请 → 批准，角色 `user`，id=2），装入同一个 SSE 观察钩子后登录 | 浏览器（界面） | 连接建立，`hello{accountId:2,role:"user"}` |
| 给这个账号建一条事项（`owner_ids:[2]`） | **admin（curl，另一个账号）** | `10:03:05.506 items{itemId:1,kind:"created",ownerId:2}`；日历**自己**出现两个色块（9/18、9/19），面板 `今日任务1 / 多日任务清单1` |
| 改这条事项的标题并补进展 | **admin（curl）** | `10:03:20.726 items{itemId:1,kind:"updated",ownerId:2}`；色块文案自己变成新标题，面板行的「进展」也自己变了 |

两次都是**另一个账号**的动作，窗口里没有任何人操作，事件落在同一种被包装的连接上、界面自己重画。把它与 2 的「零新增」并排看，「user 收不到他人的事项事件」才是可证伪的结论：同一个窗口、同一种连接，**与我有关的动作会响，与我无关的动作一声不响**。这半条对应 spec 的 User Story 12（别人改动我可见的事项时我的窗口无需刷新就更新）。

09:48:40 `u05-inviter`（curl）建 `05-待接受的邀请事项`（2026-09-18 → 2026-09-20，标签 出差）并邀请 `u05-invitee`（`POST /api/items/5/invites {"account_id":2}` → `201`）。

| 顶栏「邀请」入口 | 由隐藏变为可见，角标 `1`（**未刷新**，09:48:40 当场出现） |
| 邀请对话框 | 标题 `05-待接受的邀请事项`；元信息 `u05-inviter 邀请你一起做 · 2026-09-18 → 2026-09-20 · 出差` |

### 4. 接受 → 不刷新即出现，且成为并列 owner 之一

在邀请对话框里点「接受」：

| 观测点 | 值 |
| --- | --- |
| 钩子账上 | `09:49:00.381 self{kind:"invites-changed"}` + `09:49:00.381 items{ownerId:2,kind:"transferred-in",itemId:5}` |
| 日历 | 出现 3 个色块（9/18、9/19、9/20），文案 `u05-invitee +1: 05-待接受的邀请事项`——`+1` 即「除自己外还有 1 位 owner」 |
| 面板 | `今日任务2 / 截止提醒1 / 多日任务清单1` |
| item 5 的 `owners` | `["u05-invitee","u05-inviter"]`（并列、无主次） |
| 角标 | 回到隐藏；`GET /api/invites` 空 |
| 「无需手动刷新」的判据 | 页面里的观察日志**从 09:47:04 连续累积到 09:49:00**——整页刷新会把它清零；日志没断，说明这一连串身份切换与接受动作全程发生在同一个文档里 |

**这条不宣称是 SSE 把事项画上去的。** 接受后界面重画，机制上由应用自己那次重取驱动（`public/invites.js` 的 `onDone` → `public/app.js` 的 `boot()`），同一条连接的 `items{transferred-in}` 事件也在同一毫秒到达（账上可见）；本票的断言只是**用户不需要手动刷新**——至于重取与推送各占多少，本票不判。这也正是它区别于 2.1 那种「我什么都没做、窗口自己变了」的观察。

### 5. 拒绝 → 不出现，且可以再邀同一个人

09:49:21 `u05-inviter` 建 `05-将被拒绝的邀请事项`（2026-09-17 → 2026-09-18，标签 个人）并邀请同一个人；被邀请人窗口角标 `1`，对话框列出该条（标题 / `2026-09-17 → 2026-09-18` / 发起人 `u05-inviter`）。

点「拒绝」之后：

| 观测点 | 值 |
| --- | --- |
| 提示条 | `已拒绝，对方可以再邀` |
| 角标 / 对话框 | 角标隐藏；对话框体变成 `没有待接受的邀请。` |
| 日历 / 面板 | 与接受之后逐字相同（`今日任务2 / 截止提醒1 / 多日1`）——**该事项没有出现**，而它 9/17→9/18 若可见会同时进今日任务、今天截止与多日三处 |
| `GET /api/items` / `/api/invites` | `["5:…","1:…"]` / 0 条 |

**再邀同一个人**改用**发起人的界面**做（顺带验 `user` 角色的邀请接线，09:50:04）：`u05-inviter` 登录 → 点日历上该事项 → 编辑对话框出现「邀请他人一起做（需要对方接受；接受之前对方看不到这条事项）」→ 勾选 `u05-invitee` → 点「发出邀请」→ 提示条 `已发出 1 条邀请，等对方接受`；`item_invites` 新增一行 `id=3 item_id=6 account_id=2 invited_by=3`，**没有**被「已经邀请过 / 已在名单里」挡住。回到被邀请人视角：`GET /api/invites` 又是 1 条（`05-将被拒绝的邀请事项（u05-inviter 发起）`），日历与面板仍不含它。

## 中途撞到、不属本票的三件

### 1. 登录后不重跑权限：`管理` 入口与邀请角标同一根因

被邀请人**在同一个页面里**登出、再登录（无整页加载）后，页面显示 `u05-invitee（user）`、`GET /api/bootstrap` 也报 `inviteCount: 1`，但顶栏「邀请」入口是隐藏的、角标空——**邀请此时无处可点**。整页加载（`boot()` 走已登录分支）则正常。

这与工单 02 的顺带发现同根因：`onLogin` 只调 `enterApp()`、不重跑 `boot()`，`state.capabilities` 与 `state.inviteCount` 停在登录前的值，而 `render()` 按它们决定「管理」「邀请」两个入口的显隐（工单 02 记的是 `管理` 那一半）。工单 02 已记录此缺陷，并把修复（`onLogin` 改走 `boot()`）留在工作区里（本票执行时尚未提交）。

**对本票的影响**：不影响第 2–5 条——那些观察走的是「整页加载后的正确状态」与「事件实时到达」两条路径，都不经过登录动作本身。修复落地后我在当前工作区的构建上复验了入口路径：未登录整页加载 → 登录 → 角标 `1` 正确（09:51:23）；实时到达 → 角标 `1 → 2` 正确（09:52:58）。**处置不在本票**：缺陷归工单 02/03，修与不修、在哪一票收口由维护者定；本票只记录「在旧构建上撞到过、在当前构建上复验已消失」。

### 2. 同宿主不同端口共用 cookie（撞到的是反向）

浏览器侧最初在 `127.0.0.1:4700` 上以 admin 登录成功，随后对同一实例的请求变成 `401 请先登录`，而该实例的 `sessions` 表里那条记录还在——这次带上来的 token 不是我这条。机型与工单 04 的附带发现 2 相同：`rili_session` **只按主机名、不按端口**区分，同机并行会话在别的 `127.0.0.1:<端口>` 实例上登录就会把它换掉。本次的规避办法是给浏览器身份换一个主机名（`localhost`），发起方走 curl 各自带 jar。该条已由工单 04 记录并建议并入 `docs/agents/local-environment.md`，本票不重复展开。

### 3. 中文经命令行传参会被改坏（新，环境细节）

用 `curl -d '{"title":"05-他人的跨日事项",…}'` 建事项：标签校验报「必须取自白名单」（而白名单里就有 `会议`），落库的标题是一串 `U+FFFD`——Git Bash → curl 这条路径把 UTF-8 中文改坏了。改用 `--data-binary @payload.json`（文件以 UTF-8 写入）后一切正常。判据要把库里的文本按**码点**打出来核对（`\u4ed6\u4eba…`），别信终端回显——终端本身也会显示成乱码。这条是「命令行传参」这一层的坑，与 `local-environment.md` §1 里「PowerShell 整段要用单引号」同族；**是否并进 `docs/agents/local-environment.md` 由维护者定**（那份文档是环境事实的唯一出处，本票不擅自改它的既定内容）。

## 未做的事

- **没有观测发起人窗口的实时更新**：一次只能持有一个浏览器身份，接受邀请时只有被邀请人的窗口在观察；服务端确实也向 `ownerIds:[3]` 推了事件，但那半边的**界面**没被看到。
- **「用界面发起邀请」只走了一次**，而且是第 5 条那次**再邀**（拒绝之后）；第 3 条首次邀请是 curl 发的。也就是说：`user` 角色的邀请对话框接线是通的，但「第一次邀请」这条路本票没有从界面走过。
- **没有铺边界情况**：重复邀请、邀请已在名单里的账号、拒绝后立刻再邀的时序竞争等，属于领域测试的地盘（spec 的 Out of Scope 也是这么定的）；本票只走主路径。
- **没有动任何产品代码**：本票是验证票，只写这份工单。
- **没有把 SSE 钩子留在页面上**：它是本次验证的临时观察器，随页面关闭而消失。

## 复现

```bash

curl -s -c /tmp/j05-admin.txt -X POST http://127.0.0.1:4700/api/login \
```
