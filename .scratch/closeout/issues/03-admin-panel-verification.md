# 03 — 管理面板验证：注册申请 → 批准 → 登录 + 改角色

**What to build:** 在一次性隔离实例上，把「访客提交注册申请 → 管理员批准 → 新账号登录」这条团队拿到账号的唯一路径，连同管理面板的其余动作，在真实浏览器里走一遍并记录观察值。这条路径此前只有领域逻辑与接口层的测试，界面接线从未被操作过。

**Blocked by:** None — can start immediately.（建议与 02、04、05 共用一个浏览器会话与一个实例）

**Status:** resolved

> **原先写在这里的执行前提已失效。** 工单 02 记下的「登录之后必须刷新一次页面才有『管理』按钮」——本票动手前实测复现了两次——**已在本票内修掉**（`onLogin` 改走 `boot()`，见「本轮修掉的四处缺陷」第 1 条），修后三次表单登录都在不刷新页面的情况下拿到了「管理」入口。`.scratch/closeout/issues/02-retest-narrow-topbar.md` 与 `.scratch/browser-verification/issues/06-narrow-window-topbar.md` 的 Comments 里那段关于「未提交、一旦落地即失效」的记录保持原样，作为当时的观察。

- [x] 提交注册申请之后**账号并不存在**：用申请时填的用户名登录会失败；管理面板里能看到这条待批准申请，含申请人自选的用户名与备注。
- [x] **批准那一刻账号才生成**：角色是 `user`，用申请时填的密码能登录成功。
- [x] 拒绝申请后记录消失（不留下一个否定的状态），且同一个用户名可以重新申请。
- [x] 改角色为 `manager` 后，该账号的可见范围立刻扩大到全部事项；降回 `user` 后，他人的事项立刻从其界面消失，**不需要手动刷新**。
- [x] 删账号路径的界面提示被观察到：它作为唯一 owner 的未归档事项必须先转移，转移完成后删除成功；与别人共享的事项只是把它从 owner 名单里摘掉、事项本身留着。
- [x] 归档视图在界面上确认为**只读**：能看到已归档事项，但没有任何可改动它的入口。
- [x] 证据写进本工单：环境（端口、库、账号）、操作步骤、观察到的具体现象与结论；凡是用到绕过浏览器指针管线的点击方式，按方法论文档的要求标注出来。

## 结论

**六项界面行为全部走通；走的过程中撞出四处界面接线缺陷，就地修掉并在同一实例上逐条复验。** 四处只动前端（`app.js` / `admin.js` / `util.js`），未动领域逻辑与接口，`npm test` 88 项仍全绿。

第一处**不修则本票根本做不完**：登录后「管理」入口不出现，管理面板进不去，而 README 教给 `admin` 的第一步操作就是点它。第二处卡在紧接本票的路径上（批准新账号后马上给他派事，选不到人）。第三、四处是本票要验的视图里显示的错数据：归档视图的 owner 列永远是空的、面板时间比本机时间早 8 小时。

两处只能绕过界面完成，均在下文标注：**「转移事项」**（产品用 `window.prompt()` 让人输入序号，IAB 内嵌浏览器禁用它）与**「改角色触发对方窗口自更新」**（浏览器会话共用同一个 cookie，admin 与 bob 无法在同一个浏览器里同时在线）。

本票基于 `0b16bf1`（并行做完的工单 02、04、05 的收尾提交）之上；产品侧只有顶栏样式被那些提交动过，不影响管理面板。

## 证据

点击方式：**本票所有点击都是 `locator.evaluate(el => el.click())` 的 DOM 派发**（方法论文档记过，本环境下 `locator.click()` 会超时）。因此下面的断言证明的是**应用自身的交互逻辑**正确，不能证明「该按钮在真实鼠标下可点」。原生 `confirm` 弹窗用 `tab.getJsDialog()` 读取类型并确认。

### 1. 申请阶段不产生账号；面板能看到申请（含用户名与备注）

```
访客（未登录）提交：用户名 bob / 密码 bobpass123 / 备注「我是 bob，产品组，想一起排 9 月的计划」
  #apply-form [data-msg] → kind=ok  「申请已提交。管理员批准后才能登录。」
  提交后表单被 reset（三个字段都为空）
立刻用 bob / bobpass123 登录
  #login-form [data-msg] → kind=error 「用户名或密码不正确」；#app 仍 hidden
admin 登录 → 管理 →「待批准申请」
  表头：用户名 / 备注 / 提交时间 / 操作
  唯一一行：bob | 我是 bob，产品组，想一起排 9 月的计划 | 2026-09-18 01:44 | 批准 拒绝
  末行提示：「批准后账号立即生成，角色为 user（之后可在「账号」里调整）。拒绝会删除该申请，对方可重新提交。申请里的密码已加密存储，任何人都看不到明文。」
```

结论：**申请只落在申请表里，账号确实不存在**；申请人自选的用户名与备注在面板上如实可见（备注与提交内容逐字一致）。

### 2. 批准那一刻账号才生成（角色 `user`），申请时的密码可登录

```
点「批准」→ toast「已批准，账号已生成」；请求列表变成「没有待批准的申请。」
「账号」表：admin 自己 | admin | 0 | 0      bob | user | 0 | 0
登出后用 bob / bobpass123 登录 → 成功；#whoami = 「bob（user）」
  同时「管理」入口保持隐藏（user 没有 managesAccounts）、日历空、三个面板计数都是 0
```

### 3. 拒绝后记录消失，同名可重新申请

```
访客用 carol 提交（备注「我是 carol，运营组，要跟排期」）→ 面板出现该行（提交时间 2026-09-18 01:48）
点「拒绝」→ 原生 confirm（type=confirm）→ 确定 → toast「已拒绝」；列表「没有待批准的申请。」
用 carol / carolpass123 登录 → 「用户名或密码不正确」（拒绝没有留下账号）
同一用户名再次提交 → 「申请已提交。管理员批准后才能登录。」——不是「该用户名已有一条待批准的申请」
  库里核对：被拒的那条（id=2）已删除，只剩新的一条（id=3）
再次批准 → 账号生成；「账号」表出现 carol | user | 0 | 0
```

结论：拒绝是**记录消失**而不是留一个「已拒绝」状态，所以同名可以重新申请。

### 4. 改角色：界面两个方向 + 可见范围立刻变化（无需刷新）

界面侧（admin 在「账号」表上点）：

| 操作 | toast | 该行角色胶囊 | 该行操作按钮 |
| --- | --- | --- | --- |
| 点 bob 行的「改为 manager」 | 角色已更新 | `user` → `manager` | 改为 user / 改为 admin |
| 再点「改为 user」 | 角色已更新 | `manager` → `user` | 改为 manager / 改为 admin |

可见范围（bob 的窗口；变更由 HTTP 层发起，原因见「环境限制」）：

| 时刻 | `#whoami` | 日历色块 | 今日任务 / 多日任务清单 |
| --- | --- | --- | --- |
| 提权前 | bob（user） | 只有「bob: 整理 9 月排期」（18/19/20） | 1 / 1 |
| 提为 manager 后 | bob（manager） | 多出「admin: 季度复盘」(18)、「admin +1: 9 月复盘会」(21/22) | 2 / 2 |
| 降回 user 后 | bob（user） | 又只剩自己的三格 | 1 / 1 |

判据：三次读取的 `performance.timeOrigin` **完全相同**（`1789696031526.7`）——全程是同一个文档，没有 reload、也没有手动触发刷新。为什么只可能是那条 `self` 事件：`changeRole` 返回的变更描述里只有一条账号定向的事件（`server/accounts.js`），而 `publish` 对它的送达方式是 `broadcastToAccount`（`server/sse.js`）——角色变更**不发任何 `items` 事件**，所以这次刷新不可能来自 `items` 那条监听。这正是「越权数据必须立刻消失」在界面上的样子。

### 5. 删账号路径

```
bob 是「整理 9 月排期」的唯一 owner（该行「未归档事项」= 1）
  点「删除」→ 原生 confirm → 确定 → toast「该账号名下还有 1 条未归档事项，请先转移给他人」；bob 行仍在
转移（HTTP 层，见「环境限制」）：POST /api/admin/accounts/2/transfer {"to_account_id":1} → {"ok":true,"moved":1}
  面板重渲染后：bob 未归档 0；admin 未归档 3
再点「删除」→ confirm → 确定 → toast「账号已删除」；bob 行消失
  日历 18 号：admin: 季度复盘 + admin: 整理 9 月排期（被转移的事项活着，owner 换成 admin）
carol 只有共享事项（9 月复盘会，owner = admin + carol）→ 直接删除成功，无转移提示
  日历 21 号：「admin +1: 9 月复盘会」→「admin: 9 月复盘会」——事项留着，只是把 carol 从 owner 名单里摘掉
误点 admin 自己的「删除」：toast「不能删除自己的账号」（服务端 409，界面如实回显）
```

结论：两道闸门都在界面上如实呈现——**唯一 owner 的未归档事项必须先转移**；**共享事项只摘名字、事项本身留着**。删完后「账号」表的计数与库里的 `item_owners` 一致。

### 6. 归档视图只读

```
admin 打开「季度复盘」→ 对话框底部：删除 / 标记完成 / 取消 / 保存
点「标记完成」→ 原生 confirm → 确定 → toast「已标记完成（已归档）」；对话框关闭；日历上该事项消失
管理 →「归档」：
  表头：颜色 / owner / 标题 / 标签 / 起止 / 归档时间
  一行：（色点）| admin | 季度复盘 | — | 2026-09-18 → 2026-09-18 | 2026-09-18 09:54
  该视图内 button 数量 0、input/select/textarea 数量 0
  末行：「归档是只读的：这里只能查看，不能恢复为未完成。归档不可逆是刻意的设计，见 ADR 相关的设计记录。」
「账号」表同步为：admin 未归档 2 / 归档 1
```

结论：归档视图**只是查看**——没有恢复入口、没有按钮、没有可编辑控件；「归档不可逆」这条规则在界面上同样成立。

## 本轮修掉的四处缺陷

四处都是走界面时撞出来的。前两处让「团队拿到账号」这条路走不顺，后两处是本票要验的视图里显示的错数据，因此就地修掉并在同一实例上复验。修法都只动前端展示与接线；若认为它们该另开工单，可单独回退（`app.js` 两处、`admin.js` 三处、`util.js` 一处）。

### 1（修之前挡死本票）：登录后要手动刷新，「管理」入口才出现

| | |
| --- | --- |
| 现象 | 全新加载页面 → 以 admin 登录 → `#btn-admin.hidden === true`（此时 `#whoami` 已是 `admin（admin）`、日历已渲染）；**刷新后**同一页面才 `false`。工单 02 独立复现过两次，本票动手前又复现一次 |
| 根因 | `onLogin` 只走 `enterApp()`，不重走 `bootstrap`；而权限、角色、邀请角标都只在 `bootstrap` 里下发，于是它们停在「未登录」时的值，`render()` 按它决定显隐 |
| 修法 | `public/app.js` 的 `onLogin` 改为 `await boot()`（与 `self` 事件同一套机制） |
| 复验 | 修后三次表单登录（admin）都在**不刷新**的情况下 `#btn-admin.hidden === false` |
| 影响面 | 同一根因还会让「邀请」入口对有待接受邀请的 user 不出现、`manager` 的 owner 选择器不可用 |

### 2：批准新账号后，事项对话框的 owner 名单里没有他

```
批准 carol 后（同一会话、未刷新）打开「新建事项」→ owner 可选项 [admin, bob]
重新登录后再打开同一对话框        → owner 可选项 [admin, bob, carol]
修后：批准 dave → 不刷新直接打开   → [admin, dave]（timeOrigin 前后一致，证明没刷新）
```

根因：`state.owners` 只在 `enterApp()` 里拉一次，`admin` 事件的监听只重拉事项。修法：`public/app.js` 的 `admin` 事件里补一次 `loadOwners()`。

### 3：归档视图的 owner 列永远是空的

现象：归档一条 owner 明确是 `admin` 的事项后，归档表里该单元格是空字符串。根因：模板读 `i.owner_name`，而接口返回的是 `owners: [{id, username}]`（多 owner 改造后的字段）；这个字段名在代码里只出现在 `public/admin.js` 一处（`docs/adr/0002` 的正文以「那时候还是单 owner」的口吻提到过它）。修法：改用仓库既有的 `ownerLabel(i)`（与日历色块、侧栏同一口径）。复验：该列显示 `admin`。

### 4：面板时间显示 UTC，界面其余部分都是本机时间

现象：bob 申请的「提交时间」显示 `2026-09-18 01:44`，而当日本机时间是 09:44（库里 `created_at = 2026-09-18T01:44:26.969Z`）；归档时间同样（01:54 vs 09:54）。根因：直接对 ISO 串切片显示。修法：`public/util.js` 新增 `formatDateTime(iso)`（换本机时间、格式不变），`public/admin.js` 两处改用它。复验：两列分别显示 `2026-09-18 09:57`（提交）与 `2026-09-18 09:54`（归档）。

## 环境限制与未做的事

- **「转移事项」的界面路径在本环境走不通**：它用 `window.prompt()` 让 `admin` 输入序号，而 IAB 内嵌浏览器禁用 `prompt`——点「转移事项」后弹出的是一条红色错误 toast `prompt() is not supported.`（面板状态不变）。因此转移这一步改用 HTTP 层并在此标注。这不代表产品在普通浏览器里坏了，但说明这条 UI 依赖一个在部分内嵌 webview 里被禁用的 API。
- **角色变更的「无需刷新」也是这样触发的**：改角色本身在界面上验过（证据 4 的界面那两条），但要让 bob 的窗口在线等这条推送，就必须让 bob 保持登录，而 IAB 各标签页共享 cookie、同一个浏览器里没法同时是 admin。故这一次变更由 HTTP 层发起；判据（timeOrigin 不变、色块增减）仍然只反映前端行为。
- **会话 cookie 在并行会话之间互踢**（本票最初写成「IAB 会随机丢 cookie」，此处已更正）：本票进行中浏览器侧的会话反复失效，而服务端 `sessions` 表里对应行仍然有效。真正的原因是 **`rili_session` 只按主机名区分、不按端口**——本机同时有多个会话各起一个实例（都在 `127.0.0.1`、只有端口不同），任何一方在浏览器里登录就会把别人在这个主机上的 cookie 换成自己的。并列的工单 04 与 05 各自撞到并记录了它（04：改绑 `127.0.0.2` 之后整轮未再复现；05：浏览器侧改用 `localhost`、他人的动作从 curl 发起）。**规避**：给每个身份一个不同的主机名（`localhost` / `127.0.0.2`），或接受它并在每次动作前确认登录态——本票用的是后者（失效即重新登录），结论不受影响。
  副产品（产品行为，值得记一笔）：会话失效时界面会停在「僵尸登录态」——顶栏仍是 `admin（admin）`、日历还在，下一步动作却报 toast `请先登录`，且不自动回登录页。
- 没有为这三条路径新增自动化浏览器测试（spec 明确不做）；未覆盖的边界情况（重复邀请、邀请已在名单的账号、删账号时唯一 owner 的各分支）按 spec 不做界面验证。

## 复现

```bash
# 起实例（完整命令见 docs/agents/local-environment.md §1）
powershell.exe -NoProfile -Command '$env:RILI_DB="./data/verify-03.db"; $env:RILI_ADMIN_USER="admin"; $env:RILI_ADMIN_PASSWORD="verify03-admin-pw"; $env:PORT="4800"; $env:HOST="127.0.0.1"; Start-Process -FilePath "node" -ArgumentList "server/index.js" -WorkingDirectory "D:\rili" -WindowStyle Hidden -RedirectStandardOutput "D:\rili\data\verify-03.out.log" -RedirectStandardError "D:\rili\data\verify-03.err.log"'
netstat -ano | grep ':4800 ' | grep LISTENING      # 拿 PID

# 浏览器（IAB）打开 http://127.0.0.1:4800/ ，按上面的 1–6 顺序操作；每次动作前若已会话失效，
# 重新登录即可（服务端会话仍有效，见「环境限制」）
#   申请账号页签提交 bob → 登录页签用 bob 登录（应失败）→ 登录 admin → 管理 → 批准
#   → 账号页签改角色 → 删除/转移 → 归档 → 管理 →「归档」

# 收尾
powershell.exe -NoProfile -Command "Stop-Process -Id <pid> -Force"
rm -f data/verify-03.db* data/verify-03.*.log
```
