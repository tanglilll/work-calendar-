# 收尾（closeout）——第二轮浏览器验证与环境事实落盘

Status: ready-for-agent

## Problem Statement

产品已经写完了：代码在 `main` 上、已推到远端、`npm test` 88 项全绿，仓库工作区干净。但**「测试全绿」与「这东西真能用」之间还隔着三件事**，而它们恰好都是自动化测试照不到的地方：

- **团队拿到账号的唯一路径没人走过。** 「注册申请 → 管理员批准 → 登录」是 README 教给使用者的第 2、3 步操作，但批准、拒绝、改角色、删账号、归档查看这五个管理动作，在浏览器里从未被操作过一次。这条路上任何一处接错，整个团队都进不来，而 `npm test` 全绿。
- **防止静默覆盖的唯一机制没人见过。** 每条事项带 `version`，编辑冲突返回 `409 VERSION_CONFLICT`。这条决策的逻辑有单测（`test/items-flow.test.js`），但**提示有没有真的出现在界面上、对话框冲突后是什么行为**，从未被观察过。乐观锁是「不静默覆盖他人改动」这项承诺的全部实现。
- **可见性过滤在真实浏览器里没人验过。** 「服务端过滤、前端不被信任」是本项目最重要的安全承诺，它在纯判据层与 HTTP 层都有测试，但真实浏览器里一个 `user` 账号**是否真的收不到他人的事项事件**、被邀请人接受邀请后**是否不必刷新就能看到事项**，都没看过。后者顺带牵连一条从未在界面上出现过的领域规则：「邀请不是参与者状态，待接受期间被邀请人看不到该事项」。

与此同时，有两条知识只存在于**仓库之外**：交接文档躺在 `%TEMP%`（随时会被系统清理），里面记着几条别处查不到的实机环境事实——用 ZCode 后台任务跑服务会连带杀掉同工作区其它 node 服务、`cdn.jsdelivr.net` 不可达会导致依赖它的 HTML 静默退化、`node:sqlite` 返回的行对象是 null 原型会让 `assert.deepEqual` 以「两边打印一模一样」的方式失败。**这些坑一旦随临时文件消失，接手的人会一模一样地重踩一遍。**

最后，仓库里现存的指引有几处与现实不符：`docs/agents/issue-tracker.md` 声称「本仓库没有 git remote」，而远端早已存在且 `main` 已推上去；`master` 分支停在旧基线且无任何独有提交；工单 06（窄屏顶栏）是唯一开着的缺陷，已有量化证据与三个候选修法，等一个决策。

## Solution

把「已完成」这句话变成可信的，做法是**在隔离环境里把三条关键路径真实走一遍并留下可复算的证据**，同时把只存在于仓库外的环境事实落进仓库：

1. **窄屏顶栏缺陷（工单 06）**：采用「整块折行」修法（已实施），并在第二轮浏览器验证里复测四个宽度，通过后关闭工单。产品口径随之明确为「≥700px 是可用宽度」。
2. **第二轮浏览器验证（新工单 07–09）**，只走主路径，不铺边界情况：
   - 注册申请 → 批准 → 登录 + 改角色（管理面板的界面表现）；
   - 两窗口同账号编辑同一事项 → `409` 的界面表现；
   - `user` 账号的 SSE 可见性烟雾测试 + 接受邀请后不刷新即出现。
3. **环境事实落盘**：新建一份 agent 环境文档，收进只存在于 `%TEMP%` 的几条实机事实，并修正 `issue-tracker.md` 的过期表述。

验证在**一次性隔离实例**上做：独立进程、空库、独立端口，验完整库删除——与开发实例、演示实例完全隔离。

## User Stories

1. 作为项目维护者，我想要三条只在浏览器里才看得见的关键路径被真实走过一次，这样我交给团队的是一个点得通的产品，而不是一个「测试全绿」的假象。
2. 作为项目维护者，我想要收尾完成后仓库里没有开着的工单、没有与现实不符的文档、分支列表没有歧义，这样「已完成」这句话才是可信的。
3. 作为下一个接手的人，我想要每条验证都留下可复算的证据（操作步骤、观察到的现象、结论），这样我能判断结论在什么前提下成立，而不是只能选择相信。
4. 作为下一个接手的人，我想要环境坑有单一的、在仓库里的文档，这样我不必去 `%TEMP%` 或对话记录里考古。
5. 作为团队成员，我想要「注册申请 → 管理员批准 → 登录」这条唯一的上车路径被验证过，这样我能拿到账号开始用。
6. 作为管理员，我想要批准与拒绝注册申请这两个动作在界面上被操作过，这样我不必担心某个按钮接错了接口、把整个团队卡在门外。
7. 作为管理员，我想要改角色在界面上被操作过，这样把某人提为 `manager` 或降回 `user` 时，我知道对方的界面会按新权限立刻重来、越权数据会立刻消失。
8. 作为管理员，我想要删账号前的「唯一 owner 未归档事项必须先转移」提示在界面上被看到过，这样我清楚自己正在删掉什么。
9. 作为管理员，我想要归档视图在界面上被确认是只读的，这样「归档不可逆」这条规则在界面上同样成立，而不只是服务端成立。
10. 作为事项的 owner，我想要两窗口同时编辑同一事项时看到「此事项已被他人修改，请刷新后重试」，这样我不会静默覆盖别人的改动。
11. 作为事项的 owner，我想要冲突之后对话框的行为是明确的（不把我的编辑卡在半开状态），这样我下一步该做什么不需要猜。
12. 作为事项的 owner，我想要别人改动我可见的事项时我的窗口无需刷新就更新，这样我看到的永远是同一份数据。
13. 作为 `user` 角色的账号，我想要别人的事项既不进我的日历、也不通过推送漏给我，这样「服务端过滤、前端不被信任」这条承诺在真实浏览器里也被证实。
14. 作为被邀请人，我想要待接受期间在日历与三个面板里都看不到那条事项、只在顶栏「邀请」入口里看到标题与日期，这样「邀请不是参与者状态」这条领域规则在界面上成立。
15. 作为被邀请人，我想要接受邀请后事项立刻出现在我的日历里、不必手动刷新，这样我不必怀疑「是不是该点一下刷新」。
16. 作为分屏办公的团队成员，我想要窗口变窄时顶栏按钮仍然点得到、文字不竖排，这样我不必为了点「新建事项」把窗口拉大。
17. 作为未来动手改顶栏的人，我想要窄屏行为有一条明确口径（≥700px 保证好用），这样我不必猜上一次为什么这么写、也不会误以为窄屏是待办。
18. 作为项目维护者，我想要验证在一次性隔离实例上进行、验完整库删除，这样我自己的实例与数据全程不受影响，仓库里也不留下一堆只能靠猜的数据库文件。

## Implementation Decisions

**窄屏顶栏（工单 06）——决策：整块折行。** 顶栏容器允许折行，顶栏的每一块禁止在内部断行、禁止被压扁，右侧按钮组允许自行分行。这样任何宽度下都不会出现竖排文字或被裁掉的按钮，且不需要任何 JavaScript。被否掉的三个候选：顶栏横向滚动（要让用户自己发现「顶栏能滚」）、窄屏折叠次要按钮（要在这个刻意保持前端轻的零依赖项目里新增菜单组件、开关逻辑与键盘可达性）、声明不适配窄屏（把代价转嫁给分屏用户，而 700px 就开始换行说明分屏是常见用法）。配套的产品口径写进 README 的「已知限制」：**≥700px 是可用宽度**，更窄只保证不裁切、按钮可点——日历固定 7 列，420px 时每格约 55px，色块文案本就读不出来，那是列数决定的，与顶栏无关。精确规则与实测数据留在工单 06，不在此处复制。**不为此写 ADR**：纯样式、随时可回退、不违反直觉。

**验证范围——三条全做，只走主路径。** 边界情况（重复邀请、邀请目标已在名单、删账号时唯一 owner 的各分支）不做界面验证，因为领域测试已覆盖；本轮的目的是确认界面接线通、领域规则在界面上可见，而不是再测一遍领域逻辑。

**语言与术语**：本 spec 及后续工单一律使用 `CONTEXT.md` 的词汇——事项、owner、邀请、进展、归档、账号、角色（`user` / `manager` / `admin`）、注册申请；「管理员」是口语合称，特指最高权限时一律写 `admin`。本轮不新增术语，`CONTEXT.md` 无需改动。

**接缝——只用现成的，不新增。** 项目已有三层：浏览器层（真实界面，本轮三条路径的落点）、HTTP 层（桩 req/res 直接喂给接口处理函数，已在邀请接口测试中使用）、领域层（内存库 + 走真实申请/批准路径造账号的测试世界）。本轮要验的三条路径，风险全在最外层的浏览器接线，服务端那一半已被 HTTP 层与领域层覆盖，因此**不为本轮新增任何接缝**，也不为这三条写自动化测试。

**隔离实例**：独立进程启动（不能用 ZCode 后台任务，否则回合结束被清理且可能连带杀掉其它服务）、空库、独立端口，验完整库删除。**不复用演示实例**：它的库里有 31 条演示事项与 3 个账号，今天那格已被「+N 项」折叠，且其中一个演示账号被提权为 `manager`——用它验「`user` 只看得见自己的事项」会得出错误结论。空库反而更理想：没有任何遗留事项干扰渲染断言。

**记录落点**：本轮工单全部放在本 spec 同目录的 `issues/` 下、从 `01` 起编号——一个 spec 一个目录，符合仓库已声明的 tracker 约定；编号顺序即依赖顺序（前置文档在最前、收口核对在最后）。验证方法论文档不再容纳新工单，只在本轮收口时把「本次未覆盖」那三条改为指向新工单；它仍是浏览器层方法学（可靠点击方式、共享标签页风险、实例隔离）的唯一出处，新的环境文档指向它而不重复其内容。

**环境事实落盘**：新建一份 `docs/agents/` 下的环境文档，与既有的领域文档、issue tracker、triage 标签三份并列；内容为四条实机事实——后台任务连坐杀服务与正确的独立进程启动方式、CDN 可达性、`node:sqlite` 行对象的 null 原型断言陷阱、GitHub 需经本机代理转发。同时修正 `issue-tracker.md` 里「本仓库没有 git remote」这句过期表述。

**产品名统一为「工作日历」（2026-09-18 决定）。** 界面侧已经是这个名字（页面标题、登录页标题、顶栏品牌三处一致），要跟着对齐的是文档：`CONTEXT.md` 的首行与 README 的首行。`CONTEXT.md` 是词表，产品名变了它首行必须跟着变。历史工单里出现的旧称属于当时的观察记录，不改写。

**分支终局**：日历样式原型分支以 tag 形式存档（保留四个样式变体与一次性演示启动器），分支本身删除。不把它提升为常驻脚本——它写的是旧载荷形态，直接跑会把演示事项静默全归到一个账号名下；而它服务的是一类目前并不存在的需求。

## Testing Decisions

**什么算好测试**：只断言外部可观察的行为——界面上出现的文案、DOM 里的行数、面板里的计数、别人窗口里出现的色块——不碰实现细节，不为了可测性改变产品代码。每条结论必须**可复算**：记下环境（端口、库、账号）、操作步骤、观察到的具体数值与结论。凡是用到「绕过浏览器指针管线」这类非常规操作方式的断言，必须在工单里标注，因为它证明的是应用自身逻辑正确，而不是「该按钮在真实鼠标下可点」。

**各层职责**（沿用第一轮，不新增接缝）：
- 浏览器层：真实界面行为，本轮三条路径唯一该验的层，手工驱动、把证据写进工单；
- HTTP 层：接口形状、状态码、越权，已有先例；
- 领域层：可见性判据、日期不变量、颜色、邀请与账号规则，已有先例，本轮不扩展。

**回归护栏**：改动后跑既有测试套件（88 项），确认没有退步。窄屏修法只动样式与文档，预期不受影响——这正是它该给出的结果。

**先例**：工单 06 的宽度—行数证据表（用测量而非目测）、工单 05 的双窗口「可证伪」验证（不只看有没有出现，还要求能说明为什么它不可能因为缓存而出现）、以及方法论文档里「只有一种点击可靠」那张对照表。本轮沿用同样的证据标准：**先写清验收标准，再操作，再记录观察值，再给结论。**

**刻意不做的**：不为这三条路径写自动化浏览器测试。它们需要真实浏览器与多标签页协作，自动化成本高于收益，而它们要防的是「接线错了」，一次性人工走通即达成目的。

## Out of Scope

- **边界情况的界面验证**：重复邀请、邀请已在名单的账号、删账号时唯一 owner 的未归档事项等——领域测试已覆盖。
- **手机端适配与响应式重构**：本轮的窄屏决策明确「≥700px 是可用宽度」，更窄只保证可点，不做进一步适配。
- **SSE 在服务端的进一步测试**：可见性判据与 HTTP 层已有测试，本轮只在浏览器里做烟雾确认。
- **前端自动化测试体系**：项目零依赖、无构建、无浏览器测试运行器，本轮不引入。
- **推送到远端**：远端 SSH 需经本机代理转发，代理未运行时只能本地提交；推送不在本 spec 的判定范围内。
- **纯 HTTP 与 scrypt 同步阻塞等既有技术限制**：已在 README 记录，不在本次收尾内。

## Further Notes

**`master` 分支。** 它停在 `e18a74b`，已核实是 `main` 的严格祖先、没有任何独有提交，也不在远端（远端只有 `main`），属于纯本地遗留。删掉不丢任何东西，但它不在本轮已定的决策里，故留在原处待你定。

**执行顺序建议。** 复测工单 06 与三条验证共用一个浏览器会话，一次起实例就把四件事做完；先前置的零风险动作（分支 tag 存档、文档修正）先做掉，避免浏览器会话被杂事打断。每条验证各自独立成工单，互不阻塞，可以任意顺序执行。

**应急口径。** 若复测发现 420px 下仍然横向溢出（工单 06 警告过「只加不换行属性会加重溢出」，本次同时加了容器级折行，理论上不会），则回退到工单原本列的「顶栏横向滚动」或「声明不适配窄屏」，并把实测数字写回工单再决策。

**为什么这些验证值得做，而不是「服务端已经测过了」。** 服务端测试证明的是规则本身正确；浏览器验证证明的是**用户真的会看到这个结果**。两者之间隔着模板渲染、事件委托、对话框生命周期与 SSE 重连——第一条没人走过、第二条没人见过、第三条没人观察过，而它们分别对应「团队进不来」「改动被静默覆盖」「数据越权可见」三种最贵的失败。
