# 第二轮架构深化：八个候选（arch-deepening-2）

Status: ready-for-agent

## Problem Statement

产品的功能与验证都已收口（18 张工单全 resolved、测试 97 项全绿、`main` 与远端一致），但一轮架构审查在代码里找到八处会持续制造摩擦的结构。它们不是「不够漂亮」，而是**已经在制造实际损失**：

- **字段定义没有落点。** 校验层输出的 keys 同时是 SQL 列契约，却没有任何地方声明它：更新路径靠动态 `SET` 自动跟上字段，新建路径要人工同步列清单——`21b42ba` 那条**静默丢数据**的 bug 就是这个结构的直接产物，而结构还立着，同类漏列会再来一次。
- **变更描述协议没有落点。** 谁可以发哪种变更、owner 名单变化要通知谁，由四个领域 module 各自手写；owner 差分被抄成三份；`publish` 用 if/else 认三个 `to`，拼错即**静默丢弃**。
- **权限判据的输入是过期副本。** 可见性判据本身是纯函数、测得也足，但 SSE 客户端里存的是**连接那一刻的 role 快照**：把一个人从 `admin` 降为 `user`，他的旧连接仍会收到 admin 事件。这是「服务端过滤、前端不被信任」这条承诺在长连接上的缺口。
- **同一套门有两份，其中一份还漏了一道。** 「能不能动这条事项」在 items 与 invites 各写一遍，invites 那份**没有归档检查**——给一条已归档事项发邀请，领域层会接受，且经 REST 可达。
- **依赖注入没画到广播中枢。** 组合根注入到了 items/accounts/sessions/invites，SSE 却是模块级 `clients`：多个组合根共享一套，测试里 A 的广播会到 B 的客户端，而「谁收到了什么」根本无法断言。
- **前端的状态刷新规则散在八处。** 「哪个事件之后要重拉 state 的哪些字段」没有单一归属，`refresh` 与 `boot` 两级粒度混用——上一轮四处界面修复里有三处同一根因（登录后「管理」入口要刷新才出现）。
- **最纯的 module 零判据，而它们旁边只能浏览器验的部分刚花掉两轮手验。** `calendar.js` / `sidebar.js` 是纯函数但 `test/` 从不导入它们；`items-flow` 的邀请两分支、`itemform` 的值对象→payload 映射、admin 面板的视图迁移同样零覆盖。README 里白纸黑字写着的那条分桶不变量（逾期基线 = 已逾期 + 今天截止），一条断言都没有。
- **交互约定有 2–3 套。** `data-act` 词汇不一致（`cancel` vs `close`）、开框仪式三个文件各抄一遍、错误呈现两条路径、会话的公开端点豁免靠每个方法上的 flag——都靠「记得」对齐。

## Solution

按 **两段推进、段内串行**做完八个候选：**服务端 A → E → B → C → D**，**客户端 G → F → H**。每张票走「红→绿判据 + 全量套件」，一笔提交进 `main`；每段结束打一个 tag 并做一次浏览器冒烟。

顺序本身是决策的一部分，理由是**文件重叠**：服务端五个候选都压在 `items.js` / `accounts.js` / `invites.js` / `sse.js` 四份文件上，客户端三个压在 `itemform.js` / `admin.js` 上。并行会互相踩，所以段内串行不是偏好而是约束。**E 必须先于 B、C**：广播中枢不做成可注入的 module，「谁收到了什么」就断言不了，B 与 C 只能靠代码审阅验收——而 C 恰恰是那个「未构造复现」的候选。

## User Stories

1. 作为项目维护者，我想要「一条事项有哪些字段」只有一处定义，这样新建与更新两条写路径不会再各自漏列，`21b42ba` 那类静默丢数据不再可能。
2. 作为下一个接手的人，我想要一条测试能对**每个可写字段**断言「新建带上它 → 落库后原样返回；更新带上它 → 同样」，这样新增字段时忘了接线会立刻变红，而不是等用户在浏览器里发现。
3. 作为项目维护者，我想要变更描述（谁发给谁、哪种 kind）有一个 module 负责，这样理解「改名单推给谁」不必跳五个文件，owner 差分也只算一次。
4. 作为项目维护者，我想要非法变更**无从构造**（而不是发出去被静默丢弃），这样拼错 `to` 会在测试里炸，而不是在生产里静默消失。
5. 作为被降权的账号，我想要权限变更后我的界面**立刻**按新角色收数据，这样我不会通过一条旧连接继续看到我不该看的东西。
6. 作为项目维护者，我想要三条投递路径（事项事件、admin 事件、账号定向）走**同一个判据**，这样可见性规则不会在某一条路径上被绕过。
7. 作为被删除账号的持有者，我想要我的连接被断开而不是留着占位，这样服务端不留下一个收不到任何事件、却仍挂着的连接。
8. 作为事项的 owner，我想要「已归档」这件事在领域层被一致对待——读、改、归档、邀请都拒绝，这样我不会收到一条指向已归档事项的邀请（那是界面里根本看不到的东西）。
9. 作为管理员，我想要「删除已归档事项」这条今天事实上存在的能力被**写明**在门的接口里，这样它的存在是决定而不是疏漏。
10. 作为项目维护者，我想要两个组合根各持一套广播中枢，这样测试里一个实例的广播不会跑到另一个实例的客户端，我还能断言「这次变更谁收到了」。
11. 作为项目维护者，我想要入口层的错误映射有一个可测的接缝，这样「5xx 不外泄内部错误码」这条收紧过的规则有回归网，而不是测试自己重写一份。
12. 作为使用者，我想要登录之后**立刻**看到我该看到的入口（而不是要靠刷新），这样我不会以为自己的权限有问题。
13. 作为项目维护者，我想要「哪个事件重拉哪些字段」是一张可以断言的表，这样新增事件源时不会漏掉某一项（上一轮已经漏过一次）。
14. 作为项目维护者，我想要日历的网格算术与侧栏的分桶不变量有判据，这样跨月边界、42 格布局、逾期口径这些规则改动时能被拦住。
15. 作为项目维护者，我想要「逾期基线 = 已逾期 + 今天截止」这条写在 README 里的口径**第一次有断言**，这样它不会在某个改动里悄悄漂掉。
16. 作为项目维护者，我想要表单的「值对象 → payload」映射不依赖 DOM 就能断言，这样「表单加了字段但忘了收集」会被拦住（进展丢数据那类问题的镜像风险）。
17. 作为项目维护者，我想要面板的视图迁移（页签 + 转移视图）可以被 headless 断言，这样它的验收不必每次都用一轮真实浏览器会话换。
18. 作为项目维护者，我想要属性词汇、开框仪式、错误呈现、公开端点豁免各只有一处定义，且产出端与消费端**引用同一个常量**，这样改属性名不再只有浏览器能发现。
19. 作为项目维护者，我想要浏览器冒烟只用在「本质上只能在浏览器里验」的那些事上（SSE 送达、cookie 顶号、原生对话框、布局），这样验证成本花在该花的地方。
20. 作为下一个接手的人，我想要每张票的验收里写清「这条判据为什么只能这样验」，这样我不会为了省事把只能在浏览器验的东西假装用单测覆盖了。

## Implementation Decisions

### 段一 · 服务端

**A — 字段定义收成一份（模块：事项的字段表）**
- 一份字段表描述 `items` 的可写列：名字（即 SQL 列名）、解析/校验、在新建路径是否必填、默认值。校验、新建的 INSERT、更新的动态 `SET` 全部从它派生。
- `owner_ids` **不进字段表**：它写的是另一张表（`item_owners`），语义是「名单」而非行上的列；它继续走自己的校验，并在接口上说明这条区分。
- `progress_updated_at` 是派生肖：规则是「有进展才记它的更新时间」，与更新路径一致，写进表旁的说明而不是当成可写字段。
- bootstrap 不再手挑 5 个 limit，直接下发完整的 `LIMITS`（当前漏了 `PROGRESS_MAX`），并断言它与 config 同源。
- **不做**由字段表生成 DB schema：迁移成本不划算，schema 继续手写；表与 schema 的对齐由「每个可写字段的新建/更新往返」这条表驱动断言守住。

**E — 广播中枢可注入（模块：SSE 中枢）**
- 形状：`createSse()` 返回 `{ addClient, publish, broadcastToAccount, startHeartbeat, closeAll }`；组合根建好注入 `routes`，`routes.js` 不再 import `sse.js`；心跳由入口层用中枢起。
- 判据要能断言「某次 publish 之后，哪些客户端收到了什么」——这是 B 与 C 的验收基础。
- 顺手给入口层的错误映射一个可测接缝（`>=500` 不外泄内部码、只有业务错误带 code/fields）。

**B — 变更词表 + owner 差分（模块：变更描述）**
- 词表常量 + 构造函数（如 `ownerChanged(item, kind)`），让非法变更无从构造；`publish` 只接受构造出来的变更，未知 `to` 在测试里炸而不是静默丢弃。
- owner 差分（removed / added / stayed、以及「谁需要被通知」）收成一处实现，items、invites、accounts 三处共用。
- 变更仍需前端「重新拉取」的语义不变——这轮不改变投递方式，只改变「谁定义、谁构造」。

**C — viewer 的权威来源（模块：可见性判据 + 中枢）**
- 推送给谁由**推送时取权威 role** 决定，不再读连接时的快照；`broadcastToAccount` 自己做的账号比较并入判据，三条投递路径走同一处。
- **角色变更 → 重判**（连接保留，被降权者的旧连接立刻收不到 admin 事件）；**账号删除 → 断开**该账号的连接（会话已不存在，留着只是占位）。
- **先复现再修**：在 E 提供的接缝上先构造「降权后旧连接仍收到 admin 事件」的失败判据，再改。不改变「可见性在服务端过滤」这条不变量本身。

**D — 事项的门（模块：访问与生命周期）**
- 一个门 `requireItemAccess(actor, itemId, purpose)`，`purpose ∈ { read, write, archive, invite, delete }`；items 与 invites 都走它，不再各写一份。
- 对已归档事项：**读、改、归档、邀请一律拒绝**（堵上今天经 REST 可达的「给已归档事项发邀请」）；**删除是唯一例外，允许**——把今天事实上存在的能力写明，理由是删除的语义是「这事本就不该存在」，与是否完成过无关，且归档视图只读、不提供入口。
- `sessions` 表的写入归 auth（accounts 里那行直写删掉；已有 `ON DELETE CASCADE` + `PRAGMA foreign_keys = ON` 覆盖它）。
- sole-owner 谓词（同一 `EXISTS ... count = 1` 子查询写了三遍）只留一处。

### 段二 · 客户端

**G — 补上可 headless 的判据（不新增 seam、不改调用方）**
- 五处判据：`calendar`（42 格 / 周一起始 / 跨月裁剪 / 同格「先起始日期再标题」的排序）、`sidebar`（分桶不变量：逾期基线 = 已逾期 + 今天截止，两组不重叠）、`items-flow` 的邀请两分支（`invitePeople` / `respondToInvite`）、`itemform` 的值对象→payload 映射、admin 面板的视图迁移（页签 + 转移视图）。
- 后两处需要**小抽取**：把「值对象 → payload」与「视图状态迁移」变成不依赖 DOM 的纯映射；真正读 `FormData` 与触达 DOM 的那一步仍留在浏览器。
- 每个纯 module 一个测试文件，沿用 `test/` 现有惯例。断言只针对外部可观察行为，不针对 HTML 字符串。

**F — 状态与重拉的归属（模块：前端状态刷新）**
- 一张声明表：`items` 事件 → 只重拉事项；`admin` 事件 → 事项 + owner 名单 + 能力；`self` 事件 → 全部（含 capabilities 与邀请角标）；**登录之后一律全量**。一个执行器按集合执行。
- 表是纯映射，可直接断言「登录后 capabilities 一定被重拉」（正是 `f24d4e7` 的根因）。
- `state` 的形状与写入权在同一处写明；`today` 的归属一并定（日切）。
- **刻意不碰 SSE 连接逻辑**：`boot()` 目前同时取状态与建流，这轮不拆它，避免引入重连循环；声明表只决定「重拉哪些字段」。

**H — 约定变成可断言的数据（模块：前端交互契约）**
- 四项各收一处：`data-act` 词汇（统一 `cancel` / `close` 的分歧）、开框仪式（`if (open) close()` → 重建 → `showModal()` 的三个副本）、错误呈现（`result` 对象 vs `catch` 里特判 409 两条路径）、会话的公开端点豁免（与判据同居一处，而不是每个方法一个 flag）。
- 词汇做成导出常量，**产出端与消费端引用同一常量**，并加断言拦住「产出端又写回字符串」——这才是它的价值；单纯把词汇搬个位置不收敛，不做。

### 全局约束

- **提交策略**：每张票一笔提交进 `main`（提交前全量套件必须绿）；段一结束打 tag `arch/server-deepening-2`，段二结束打 tag `arch/client-deepening-2`。
- **术语**：一律用词表词汇——事项、owner、邀请、进展、归档、账号、角色（`user` / `manager` / `admin`）、注册申请；「管理员」是口语合称，特指最高权限时写 `admin`。架构词汇用 module / interface / depth / seam / adapter / leverage / locality，不用「组件 / 服务 / 接口 / 边界」。
- 与既有 ADR 无冲突：ADR-0001（零运行时依赖）与 ADR-0002（多个并列 owner）在本轮都不被触碰——B 的 owner 差分实现要保住「并列、无主次」这条语义。

## Testing Decisions

**验收标准（每张票一律）**：先有**会红的判据** → 改 → **全绿**（当前 97 项 + 新增）。能复现的先复现（C 的降权越权、D 的归档可被邀请、A 的漏列），不能直接断言的必须说明为什么只能在浏览器验。提交前跑全量套件。

**好测试的判据**：只断言外部可观察行为（接口返回的字段、判据的返回值、界面上的文案与状态），不碰实现细节、不断言 SQL 文本、不逐字符串断言 HTML。一条测试读起来应当能说明它防的是什么。

**各票的判据落点**：
- A —— 领域层。**表驱动断言**：对字段表里每个可写字段，「新建带上它 → 落库后原样返回」「更新带上它 → 落库后原样返回」。这条断言要在代码退化成手写列清单时**真的会红**（用一个临时改动证明，记录在工单里），否则它只是装饰。
- E —— 组合根层。两个 `createApp` 各持一套中枢，互不串台；某次 `publish` 之后「哪些客户端收到什么」可断言；入口层错误映射（5xx 不外泄）有回归网。
- B —— 领域层 + 中枢层。三处调用共用同一份 owner 差分；构造出的 kind 全在词表里；非法 `to` 在测试里抛错。
- C —— 先复现：降权后旧连接收到 admin 事件（红）→ 修后收不到；删号后连接被断开；三条投递路径走同一判据。
- D —— 领域层。邀请已归档事项被拒（红→绿）；改归档被拒（回归）；删除仍被允许（写下来的例外）；sole-owner 行为在三条调用路径上一致；删账号后旧会话立刻失效。
- G —— 纯函数层。五个模块各一个测试文件，断言不变量而不是 HTML。
- F —— 纯映射层。声明表可断言；「登录后 capabilities 被重拉」「`admin` 事件重拉 owner 名单」各有断言。
- H —— 契约层。产出端引用的常量与消费端一致（静态断言）；豁免清单与判据同源。

**两次段界浏览器冒烟**（用一次性隔离实例 + 独立主机名，按 `docs/agents/local-environment.md` §1/§5）：
- 段一结束：SSE 推送在真实界面上的效果（他人改动我的事项 → 我的窗口自己更新）、权限变更（降权/删号）后的界面行为、对话框仍在。
- 段二结束：三个对话框的开合与取消、错误提示路径、面板视图切换与转移视图。
- 冒烟只覆盖「本质上只能在浏览器里验」的那一列；单击一律用 DOM 派发的 `el.click()`（本环境唯一可靠方式，见 `.scratch/browser-verification/spec.md`），凡用到它的断言要标注它证明的是应用逻辑而非真实指针可点性。

## Out of Scope

- 由字段表生成 DB schema（迁移成本不划算）。
- 合并测试里三份 `freshWorld` 复制（价值低，可顺手做但不列为本轮交付）。
- `dialog.js`、`util.js`、`session.js` 的结构改动——三者已在上一轮或本轮审查中判定「删/拆不收敛」。
- 「可见性在服务端过滤」这条不变量本身、SSE 的传输方式、会话有效期与续期机制。
- H 里「把属性词汇搬进产出端」这类只换位置不收敛的动作。
- 手机端适配、CDN、依赖引入（项目保持零运行时依赖）。

## Further Notes

**八个候选从哪来。** 一轮架构审查（按改动热区定范围：初版之后改动最频繁的 `server/items.js`、`server/accounts.js`、`public/app.js`、`public/admin.js`、`server/routes.js`），原始材料是两份代码级勘察加上对承重墙的独立复核。三处曾打算当候选、复核后撤回的：上一轮已深化的 visibility 判据 / routes 薄适配 / `openDb` 接缝——不重复提，只指出「上一轮边界没画完」的部分（E、C 即属此类）。

**一处被推翻的前提，留作教训。** 审查时我告诉勘察子代理「`calendar.js` / `sidebar.js` 有测试覆盖」，实际 `test/` 只导入 `api` / `items-flow` / `session` 三个前端文件——那两个最纯的 module 是**零判据**。凡涉及「有没有测试」的判断，都要自己跑一次导入清单，不要凭印象。

**为什么 G 在客户端段排第一。** 本项目的瓶颈已经不是写代码，而是**验证代价**：紧接着的两轮（closeout、verification-fixes）为验证界面行为付出了真实浏览器手验的代价，而其中网格算术、分桶不变量、邀请分支、值对象映射、视图迁移这几类本可以是 `npm test` 里的一行断言。先铺判据，后面两票（F、H）改动 `app.js` / `itemform.js` / `admin.js` 时才有人接着。

**段内串行的约束来源，以及并行能开到多大。** 服务端四份文件（`items` / `accounts` / `invites` / `sse`）被 A、B、C、D 反复触碰，**服务端链内部不能并行**；客户端 `itemform.js` / `admin.js` 被 G 与 H 触碰，`app.js` 由 F 独占。据此可以切出三条互不抢文件的线，**最大并行度 3**：

| 线 | 顺序 | 碰的文件 |
| --- | --- | --- |
| 1 · 服务端 | 01 A → 02 E → 03 B → 04 C → 05 D | `server/items · accounts · invites · sse · routes · app · index · visibility · db` |
| 2 · 客户端源码 | 06b G（两处抽取）→ 08 H | `public/itemform · admin · invites · api · session` |
| 3 · 判据与状态 | 06a G（纯判据）→ 07 F | 新增测试文件 → `public/app.js` |

拆出 06a 的依据是实测的导出关系：`calendar` / `sidebar` / `items-flow` 已经把需要的函数导出（`buildGrid` / `assignItems` / `gridHtml` / `computeGroups` / `invitePeople` / `respondToInvite`），所以那三处判据**只新增测试文件、零源码改动**，插进哪一波都不与别人抢文件。而 `collect()` 映射与 admin 视图迁移必须先抽取（两个模块只导出对话框入口），所以那两半归 06b。

**给并行 agent 的硬规则**（共享工作区，见 `.scratch/closeout/` 里并行会话的教训）：只改自己工单列出的文件；**提交用 pathspec**（`git commit -m "…" -- <自己的文件>`），绝不 `git add -A`，不跑 `stash` / `checkout` / `branch` / `reset` / `clean`，撞上 `index.lock` 等两秒重试；不启动服务、不用浏览器（实例与浏览器是主 agent 专属，两次段界冒烟由主 agent 做）；`npm test` 若红在别人正在改的文件上，先重跑一次，持续红就如实报告，不要去修别人的东西。06b 与 08 **不允许改 `app.js`**（那是 07 的文件；这两票的改动都是模块内部，保持既有入口签名即可）。
