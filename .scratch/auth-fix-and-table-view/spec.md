# 注册报错的字段级错误 + 对照截图的表格视图（auth-fix-and-table-view）

Status: resolved

## Problem Statement

两件事，来自同一次用户反馈（各附一张截图）：

1. **注册申请提交后只显示「输入有误」。** 截图里用户名 `12313`、6 位密码、备注「测试」，点「提交申请」后表单底部只有一行红色的「输入有误」——用户看不出是哪个字段错了，也不知道该怎么改。
2. **用户给了一张别的产品的「工作日志」表格界面截图，要求审查其功能并落到本项目。** 那张表是电子表格形态：列有任务描述、任务负责人、任务状态（已完成/进行中/待开始/已延期）、项目进度（百分比 + 进度条）、预计所需天数、是否按时交付、项目进展描述、讨论群、开始日期、预计完成日期、实际完成日期、紧急重要度；顶部是工具栏（添加一行 / 表格设置 / 筛选 / 分组 / 排序 / 行高 / 填色），行按**紧急重要度**折叠分组、组头带「记录数 N」，底部是记录数统计。

## Solution

**第一件：把服务端已经给出的字段级原因显示出来。** 根因不在服务端——`POST /api/register-request` 一直返回 `400 {"error":{"message":"输入有误","fields":{"password":"密码至少 8 位"}}}`，`public/api.js` 也把 `fields` 挂到了 `Error` 上；丢的是最后一步：`public/app.js` 的 `onApply` 只写 `err.message`，而两个表单里连字段级错误的落点都没有。修法是登录与申请两个表单都加 `[data-error-for]` 落点并复用既有的 `setFieldErrors`，申请表单在**提交前**就写明密码规则。

**第二件：把截图里能用领域语言表达的部分落成项目自己的东西。** 逐项对照后，真正缺的是三个字段与一个视图：

- 新增两个可写字段：**完成度** `percent_done`（0–100 的整数）与 **紧急重要度** `quadrant`（四象限，可空 = 未标注）；
- 其余列**全部是派生量，不落库**：状态（已完成 / 待开始 / 进行中 / 已逾期）、预计所需天数、实际完成日期、是否按时交付；
- 新增**表格视图**：按紧急重要度分组、可折叠、组头带记录数、状态/象限/关键词筛选、按截止日期/起始日期/完成度排序、底部记录数统计；`admin` 可打开「显示已完成」，只读地看到归档行。

## User Stories

1. 作为申请账号的人，我想要提交失败时看到**哪个字段**错了、为什么错，这样我不必去猜密码是不是不够长。
2. 作为申请账号的人，我想要在提交之前就知道密码规则，这样我不会白填一遍。
3. 作为登录的人，我想要输错密码时看到的也是明确原因（同一条呈现路径），而不是一句笼统的失败。
4. 作为记事项的人，我想要用一个百分比表示这件事做到哪一步，这样「进展」那段文字之外还有一个一眼能比的口径。
5. 作为记事项的人，我想要给事项标上紧急重要度，这样我能按「重要且紧急 → 不紧急不重要」的顺序看今天该先做什么。
6. 作为看板的人，我想要一个表格视图把所有未归档事项摊开、按象限分组并显示每组条数，这样我不用在日历格子里找。
7. 作为看板的人，我想要按状态筛出「已逾期」、按关键词搜标题/owner/进展，这样我能只盯有问题的那几条。
8. 作为看板的人，我想要按截止日期、起始日期或完成度排序，这样我能换一个角度看同一批事项。
9. 作为 admin，我想要在表格视图里也能看到已完成（已归档）的事项，且它们是只读的，这样我不必切到管理面板去核对。
10. 作为维护者，我想要「逾期」「状态」这些口径与 `CONTEXT.md`、侧栏面板同源，这样不会出现两套互相矛盾的判定。

## Implementation Decisions

- **两个新字段走既有的字段表。** `server/items.js` 的 `ITEM_FIELDS` 是「一条事项有哪些可写字段」的唯一落点：新建的 INSERT 与更新的动态 SET 都从它派生，所以加字段不必再手写列清单。两条新解析规则：完成度接受数字或数字字符串，空 / `undefined` / `null` → `null`，非整数或越界 → `完成度必须是 0–100 的整数`；象限空 → `null`，白名单外 → 报错里列出四个合法值。
- **刻意不加 SQL CHECK。** 与既有 `tag` / `progress` 同一取舍：校验的唯一落点是 `ITEM_FIELDS.parse`，这样「新库建表」与「老库 `ALTER`」两条路径完全一致（SQLite 也无法用 `ALTER` 补 CHECK，加了必然分叉）。老库迁移走 `server/db.js` 的 `ensureColumns`（每列一道独立的门）。
- **状态是派生量，不是存储字段。** 已完成 = 已归档；否则今天 < 起始日期 → 待开始；今天 ≥ 截止日期 → 已逾期；其余 → 进行中。**「截止当天即算已逾期」与 README 里侧栏面板的逾期基线 `due_date <= 今天` 同源**，不是另立一套。预计所需天数 = 截止 − 起始 + 1；是否按时交付只对已归档行有值（归档日期 ≤ 截止日期 → 按时交付），未归档显示「—」。
- **归档行只对 admin 可见，且只读。** 没有改变「归档从一切工作视图消失」这条既有规则：普通成员的表格视图里依旧没有已完成事项，admin 打开开关时走的是既有归档接口（`GET /api/admin/archive`），行不带 `data-item-id`，点不开编辑框。
- **象限白名单只有服务端一份。** 值与顺序（顺序即分组顺序）由 `server/config.js` 的 `QUADRANTS` 定义，随 `bootstrap` 下发给前端；事项对话框的下拉也由调用点从 `state` 传入，前端不抄字面量。
- **词表与决策入库。** `CONTEXT.md` 新增「完成度」「紧急重要度」「状态」三个词条，并把「进展」的 _Avoid_ 里那两个已另有归属的词改成指向新词条；决策记在 `docs/adr/0003-percent-done-quadrant-and-derived-status.md`。

## Testing Decisions

- **领域层（`test/items.test.js` / `test/migration.test.js`）**：字段表驱动的往返断言、边界 0 / 100 / -1 / 101 / 非整数、白名单与空值、老库迁移后能读写新列。
- **前端纯函数层（`test/tableview.test.js`，48 项）**：派生口径（含「截止当天算已逾期」、跨月与同日事项的天数、归档行的实际完成日期与按时交付）、分组顺序与各组记录数、未标注组、筛选、排序、空列表。
- **表单层（`test/itemform.test.js`）**：字段表往返 + 「留空 → `null`」「越界值原样送出交服务端判」+ 选项跟着传入的白名单走。
- **表单错误呈现（`test/auth-form-errors.test.js`，14 项）**：带 `fields` 的失败 message 与 fields 都不丢、字段错误落到 `data-error-for` 元素上、密码规则与 `LIMITS.PASSWORD_MIN` 同源。
- **端到端冒烟**：内存库起真实应用、走 HTTP 接缝跑 18 项检查（注册拒绝 → 合法注册 → 批准 → 登录 → 建事项 → 越界与白名单校验 → 清空字段 → 归档 → 归档列表带着新字段）。这是本项目能自动跑到的最强一层。
- **浏览器层手验**：DOM 行为没有自动化测试运行器（零依赖项目，不引入），按惯例在一次性隔离实例上手验并把结果写进工单。
- **独立复核**：修复由**没参与修复的人**只读复核（结论 confirmed），交付声明由**没参与实现的人**逐条核对（8 条里 7 条成立，不成立的那条就是工单 03）。

## Out of Scope

- **讨论群**：项目里没有评论/群聊领域，账号之间也没有消息通道，不臆造。
- **行高 / 填色 / 表格设置 / 内联编辑**这些电子表格皮肤：与本项目「以天为最小粒度、归档不可逆」的领域无关。
- 导出、甘特图、事项之间的依赖关系。
- 浏览器自动化测试运行器（零依赖是 ADR-0001 的取舍，本轮不破）。
- **GitHub Issues**：本机没有 `gh` CLI、也没有 token，本地 markdown 仍是 tracker of record（见 `docs/agents/issue-tracker.md`）。远端仓库虽然是公开的，但 Issues 是空的。
